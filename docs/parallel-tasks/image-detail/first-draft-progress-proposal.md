# 1차 이미지 진행 표시 검토 — 2026-09-14

현재 경로는 역할별 8장의 생성과 배치 검수가 모두 끝나야 업로드를 시작한다. Mac의 `generateVerifiedFirstDraftAssets`는 검수 결과를 메모리에 누적해 전부 반환하고, `first-draft-image-lane.mjs`가 결과 바이트와 영수증을 순서대로 저장한다. DB의 부분 `verified_assets` 수령은 가능하지만 최종 `preflightAssetLineage`는 8개가 모두 저장된 뒤 한 번에 바뀐다. 따라서 현재 화면의 완료 수는 생성 중 0/8이며, 8/8 이전 개별 결과가 먼저 표시된다는 안내는 실제 계약과 맞지 않는다.

이번 최소 변경은 안내를 “8장 전체의 생성·검수를 마친 뒤 한 번에 표시합니다. 장별 검수 중 재시도될 수 있습니다.”로 바로잡는 것이다. 원본이나 검수 전 후보 이미지를 생성 완료로 표시하지 않는다. 이미지 역할 8개의 출력 파일명은 각각 고유하다. 세 역할은 병렬 생성하지만 배치 내 검수와 채택은 지정 순서로 처리한다.

장시간 생성 작업의 기존 취소 확인 폴링은 읽기만 수행해 30분 후 다른 작업자가 회수할 수 있는 상태가 되는 문제가 있었다. `20260914043300_first_draft_active_worker_heartbeat.sql`은 같은 활성 AI 토큰이 소유한 미만료 generating 작업의 기존 상태 확인을 1분당 최대 한 번 lease 갱신으로 사용하도록 제안한다. 기존 실행본을 재시작할 필요가 없다. 취소·다른 토큰·만료 상태는 갱신하지 않는다. 동일 토큰을 여러 프로세스가 공유한 경우 구분할 claim nonce는 현재 계약에 없으며, 이번 변경도 그 범위를 확대하지 않는다. 운영 적용 여부는 통합 담당의 별도 검증이 필요하다.

다음 개선안은 이번 실등록 검증 범위에 추가하지 않는다.

- 결과 확정 수와 별개로 실행 단계, 현재 역할, 장별 시도 수, 로컬 검수 통과 수, 마지막 상태 갱신 시간을 전달한다. 로컬 검수 통과를 DB 저장 완료로 표시하지 않는다.
- 부분 결과를 먼저 공개하려면 저장된 역할별 영수증·실제 바이트·현재 claim을 검증하는 별도 조회 계약을 만든다. 8개 전체 manifest와 최종 제작 승인 조건은 유지한다.
- UI는 서버의 queued/generating/cancelled/실패 원인을 구분하고, 30분 폴링 종료를 작업 실패와 구분한다. 현재는 20초 간격 90회 후 같은 작업을 다시 확인해야 한다.
- 향후 독립 heartbeat POST와 claim nonce를 도입할 경우 기존 실행본과 함께 호환 전환한다. 현재처럼 동일 토큰을 사용하는 복수 프로세스를 활성화하지 않는다.

이번 회귀 검사는 PGlite에서 상태·권한·응답 보존과 live renewal, 1분 쓰기 제한, 다른 토큰·queued·cancelled·done·expired 거절을 확인한 뒤 테스트 데이터를 롤백했다. 실제 생성 완료나 채널 등록 성공을 증명하는 검사는 아니다.
