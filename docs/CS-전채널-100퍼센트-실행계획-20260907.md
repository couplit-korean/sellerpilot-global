# SellerPilot 전 채널 CS 100% 완료 실행 계획

작성일: 2026-09-07. 최신 운영 기준 확인: **2026-09-07 02:41 KST**. 대상: Qoo10·스마트스토어·쿠팡·eBay·Lazada·Shopee·11번가·Temu.

이 문서는 현재 구현과 운영 증거를 대조한 실행 계획이다. **5차까지 구현·검증을 진행 중이며 신규 CS SQL 여섯 개는 운영 적용했다. 1~3차는 운영 배포했고 스마트스토어 단독30일 읽기2개가 실제 성공했다. 아래 채널 표는 작성 당시 기준선이며 현재 상태는 구현 진행 기록이 우선한다. 최신 구현·검증 상태는 [구현 진행 기록](./CS-구현진행-20260907.md)을 따른다. 운영 배포·실제 답변 전송 완료는 아니다.** 기존 상품 상세페이지 작업 변경은 보존한다.

## 1. 현재 상태와 목표

운영 DB `sqaoqucxakebqkiygdxb`가 보고하는 activeRelease는 `d409055526328f864d6e932d012558f14cc30071`이다. 현재 작업 폴더 HEAD `6b32850b8c623c9d28efd2a7248c0fe4fd23fd70`과 다르므로 운영 SHA 추출본을 기준으로 코드를 분석했다. 이 값만으로 모든 Vercel/worker 배포가 일치한다고 판정하지 않는다. 실제 실행 경로와 적용 DB 함수까지 배포 작업에서 다시 대조한다.

| 현재 확인 항목 | 판정 | 해석 |
|---|---|---|
| 최근 48시간 문의 조회 작업 성공 | Qoo10 364회 / 스마트스토어 125회 / eBay 367회 | API 조회 작업 횟수이며 수집 문의 건수가 아니다 |
| 같은 기간 쿠팡·Lazada 조회 성공 | 각각 0회 | 키 존재만으로 현재 CS 작동을 입증하지 못한다 |
| 내부 CS 티켓 / 수신 메시지 / 답변 전달 원장 | 각각 0건 | 외부 판매자센터에도 문의가 없다는 뜻은 아니다 |
| 실제 문의→저장→웹 표시→답변→원격 반영까지 완료 검증 | 0/8채널 | 구현률 0%라는 뜻이 아니라 전체 왕복 완료 증거가 없다는 뜻이다 |
| 기존 집중 로컬 테스트 | 58/58 통과 | 신규 범위·운영 DB·실제 전송 검증을 대체하지 않는다 |

앞서 언급한 약 50%는 구현 기반에 대한 추정치였다. 이 계획부터는 추정 퍼센트 대신 **계정·국가·문의 유형별 검증표와 완료 증거**로 관리한다.

### 100%의 정의

범위 원장은 `채널 × 실제 판매자 계정 × 국가/shop × 문의 유형 × 필수 기능`으로 만든다. 문의 유형에는 상품/주문 문의, 콜센터·이관, 일반 채팅, 반품·환불 업무, 지원 첨부, 답변 수정·재문의가 포함된다. 상태는 `미확인 / 권한 필요 / 구현 필요 / 로컬 검증 / 운영 검증 / 완료 / 제공 불가`로 분리한다.

각 범위는 다음 7개 게이트를 모두 통과해야 완료다.

1. **권한·계정**: 실제 판매자·국가·앱·shop, CS 읽기/쓰기 권한, 송신 경로와 토큰 갱신이 확인된다.
2. **신규 수신**: 외부에 생긴 실제 문의가 내부 원장과 웹사이트에 누락 없이 들어온다.
3. **과거 이력**: 복구 가능한 전체 기간과 모든 페이지·완료 상태를 읽고, 원격 원본과 건수·ID를 대조한다.
4. **답변 반영**: 정확한 문의에 답변이 한 번만 반영되고 원격 상태/내용을 확인한다.
5. **전체 대화**: 외부 작성 답변·재문의·수정·지원 첨부까지 시간순으로 보인다.
6. **장애 복구**: 재전송, 중단, 토큰 교체, 응답 유실, 동시 답변을 복구해도 누락·중복·계정 혼선이 없다.
7. **운영 증거**: 실제 적용 버전과 DB 권한을 확인하고, 정해진 관측 기간·성능 목표를 통과한다.

진행률은 확정된 범위의 필수 게이트 중 증거가 있는 통과 수 / 전체 필수 게이트 수로 계산한다. 이는 **수용 조건 충족률**이며 개발 작업량의 백분율은 아니다. 미확인 기능을 분모에서 빼서 100%를 만들지 않는다. 한 채널의 다른 국가/shop이 미검증이면 그 채널 전체 완료가 아니다.

공급자가 API를 제공하지 않거나 현재 계정 승인을 거절한 기능까지 코드로 보장할 수는 없다. 그런 범위는 전체 API 자동화 목표의 잔여 격차로 남긴다. 판매자센터 수동 처리/공식 내보내기 가져오기는 업무 커버리지로 별도 표기하며 API 100%로 계산하지 않는다. 보관 기간 이전에 플랫폼에서도 삭제된 데이터는 복구 완료로 표시하지 않는다.

## 2. 채널별 구현 현황과 실행 계획

### Qoo10 — 조회 경로는 작동, 전체 이력과 실제 답변 검증 필요

**구현됨:** 활성 자격·계정 결속, `CSCenter.GetInquiryMessage`/`SetInquiryMessage`, MSG/HELP/ITEM과 문의번호·순번을 이용한 복합 식별자, 최근 문의 조회.

**현재 빈틈:** 작성 당시 기본 조회는 최근 6일·S1뿐이었다. 3차 구현에서 S1/S2/S3 상태를 모두 읽도록 보완했으며 전체 기간 이력 복구는 남아 있다. 실제 문의의 수신·답변·원격 결과는 검증되지 않았다.

**구현 순서:** Q10-01에서 유형별 조회 기간/상태/페이지 계약을 확정하고 과거 답변까지 가져온다. Q10-02에서 외부 작성 답변, 부모 순번, 새 고객 턴과 답변 영수증을 연결한다. Q10-03에서 각 지원 유형을 실제 자료로 검증한다.

**완료 증거:** 원격 ID 목록과 수집 결과 일치, 재수집 중복 0, 실제 답변 1회 반영, 재문의만 재개방. 기존 조회 성공 횟수로 대신하지 않는다.

### 스마트스토어 — 상품·고객 문의 수신 작동, 이력 공동 차단 분리가 최우선

**구현됨:** 상품문의·고객문의 최신 조회 모두 성공. 상품문의 PUT 답변과 고객문의 POST 신규 답변, 문의 유형별 ID, DB 고정 송신 정책 true.

**확정 결함:** 과거 수집 API가 쿠팡과 스마트스토어를 공동 대상으로 요구하고 두 채널의 송신/자격 조건을 함께 검사한다. 쿠팡 정책 false 때문에 스마트스토어 단독 이력 수집까지 막힐 수 있다. 현재 이력 요청 범위도 7~30일에 한정되어 있다.

**구현 순서:** CORE-02에서 대상 채널만 검사하도록 분리한다. NAV-01에서 상품/고객 문의의 답변완료 이력까지 수집한다. NAV-02에서 신규 답변, 이미 답변된 경우, 공식 수정 API가 필요한 경우를 각각 처리한다. NAV-03에서 두 유형 모두 실제 왕복 검증한다.

**완료 증거:** 쿠팡을 차단해 둔 상태에서도 스마트스토어 이력 수집이 독립 완료되고, 두 유형 모두 과거 답변·재문의·원격 반영이 웹 대화에 나타난다. 공식 계약: [상품문의 답변 등록/수정](https://apicenter.commerce.naver.com/docs/commerce-api/current/create-or-update-answer-contents), [고객문의 신규 답변](https://apicenter.commerce.naver.com/docs/commerce-api/current/insert-inquiry-answer-pay-merchant).

### 쿠팡 — 키보다 실제 CS 실행 경로가 막혀 있음

**구현됨:** 최근 키 진단 passed, 계정 검증, requested_by 정보, 상품/콜센터 조회 및 답변 코드. NO_ANSWER·TRANSFER와 부모 답변 식별자 처리 기반.

**확정 차단:** DB 고정 송신 정책 false. 마지막 확인한 상품/콜센터 작업은 queued·시도 0회로 실제 호출 이전에 정체되어 있다.

**구현 순서:** COU-01에서 쿠팡이 승인한 실제 송신 경로를 조회·답변에 연결한다. 기존 허용 로컬/서버 경로를 활용할 수 있으나 정책 플래그만 켜서 검증을 대신하지 않는다. COU-02에서 중단 기간을 복구하고 상품문의·콜센터 미답변·이관 문의를 각각 처리한다. COU-03에서 실제 왕복 확인한다.

**완료 증거:** 승인된 경로에서 유형별 읽기 성공, 올바른 replyBy/parentAnswerId 답변, 원격 상태 일치, 중단 기간 누락 0. [쿠팡 공식 CS 워크플로우](https://developers.coupang.com/ko/workflows/cs-api-workflow)를 기준으로 검증한다.

### eBay — ASQ 일부 기능 구현, 전체 메시지함 범위 확장 필요

**구현됨:** ASQ 조회 성공, 인증된 계정, `GetMemberMessages(AskSellerQuestion)`와 `AddMemberMessageRTQ`. 전용 CS 경로에서 marketplace/item/parentMessage/recipient 검증 후 답변을 허용한다. 일반 작업 API의 답변 차단은 별도 경로 정책이다.

**현재 빈틈:** ASQ 실제 티켓/답변 검증이 없으며, ASQ만으로 일반 메시지함·주문 후 대화 전체를 수집한다고 할 수 없다.

**구현 순서:** EBY-01에서 ASQ 전체 기간/페이지/완료 이력과 답변 확인을 완결한다. EBY-02에서 실제 사용 중인 일반 메시지·주문 당사자 대화의 권한과 API를 확인해 별도 어댑터로 추가한다. EBY-03은 모든 필수 유형 검증 후 완료한다. ASQ만 준비되면 그 범위를 먼저 배포하되 eBay 전체는 부분 완료로 표시한다.

**완료 증거:** 마켓·부모 문의·수신자 일치, 원격 답변, 호출 제한/응답 유실 복구, 메시지 유형 간 중복 제거. [공식 메시지 API 구분](https://developer.ebay.com/api-docs/user-guides/static/trading-user-guide/member-communications-key-calls.html), [ASQ 답변 계약](https://developer.ebay.com/devzone/xml/docs/reference/ebay/AddMemberMessageRTQ.html).

### Lazada — IM 키는 있지만 신원 결속이 빠지고 이미지 수신 결함 존재

**구현됨:** IM app key/secret/token 보관, 서명 검증 웹훅, 초기 이력 수집과 답변 기반, 격리/중복 원장 구조.

**확정 차단:** 검증된 판매자 신원 메타데이터가 없어 현재 webhook 계정 결속 검사를 통과할 수 없다. 키가 없어서가 아니다. 텍스트 없는 이미지 이벤트가 parser에서 탈락해 ignored가 될 수 있음을 합성 입력으로 재현했다. bootstrap 시도 2건 모두 성공 기록이 없다. 예전 API 권한 오류가 현재에도 재현되는지는 미확정이다.

**구현 순서:** LAZ-01에서 실제 OAuth/GetSeller와 현재 IM 앱 승인으로 seller-country-app 신원을 결속한다. LAZ-02에서 이미지/파일/카드, 판매자 echo, 역순·재전송, IM 토큰 갱신, bootstrap 실패 재개를 완성한다. 현재 앱의 ‘자격당 1회/24시간’ 제한은 최신 공식 계약과 대조한 뒤 수정 여부를 정한다. LAZ-03에서 실제 push→웹 표시→답변→재문의까지 검증한다.

**완료 증거:** 추정 신원값 없이 실제 판매자 결속, 다른 판매자 이벤트 거부, 지원 비텍스트 메시지 누락 0, 초기 이력과 신규 push 동시 수신 중복 0. [Lazada IM 문서](https://open.lazada.com/apps/doc/doc?docId=120971&nodeId=10544)의 현재 앱 적용 조건을 확인한다.

### Shopee — 일반 인증은 존재하지만 Chat 실행 연결이 없음

**구현됨:** 키 진단 passed·계정 검증 등 공통 인증 기반. UI 내부 답변 초안.

**확정 미구현:** 현재 문의 enqueue 대상, 문의 실행 허용 목록, 원격 답변 지원 목록에서 제외되어 있다. Chat 권한 승인 여부는 아직 확인하지 못했다.

**구현 순서:** SHO-01에서 실제 partner app·국가·shop의 Chat 읽기/전송/이벤트/첨부·조회 기간 권한을 공식 개발자센터에서 확인한다. SHO-02에서 conversation/message 수집·페이지 재개·답변·원격 확인·계정 결속을 구현한다. 증거를 확보한 뒤 실행 허용을 연다. SHO-03에서 shop/국가별 실제 검증한다.

**완료 증거:** Commerce 키 검사가 아닌 Chat 권한, 과거·신규·첨부 수신, 정확한 대화에 실제 답변, 토큰 교체/재시도 복구. 문서 접근 실패를 API 부재로 처리하지 않는다.

### 11번가 — 상품 인증과 고정 송신 설정만으로 CS 연결되지 않음

**구현됨:** 상품 API 키 진단과 공통 채널 기반, DB 고정 송신 정책 true.

**확정 미구현:** 문의 동기화·원격 답변 실행이 연결되지 않았고 catalog가 공식 CS 명세/서비스 권한 확인을 요구한다. 현재 키의 상품 Q&A·긴급알리미 권한은 미확정이다.

**구현 순서:** ELE-01에서 공식 계약·현재 Key 권한·IP·유형별 필드와 상태를 확보한다. ELE-02에서 상품 parser와 별도의 CS 조회/답변/수정/재문의 어댑터를 구현한다. ELE-03에서 실제 지원 유형마다 검증한다.

**완료 증거:** 정확한 공식 endpoint와 현재 계정 샘플, 전체 이력·답변·원격 상태 일치. unsupported 표시만 해제하는 것은 완료가 아니다.

### Temu — 운영 자격부터 필요하며 반품/환불과 채팅을 분리해야 함

**구현됨:** 반품·환불 작업함 조회의 정규화 기반. 이것은 일반 구매자 채팅 구현이 아니다.

**확정 차단/빈틈:** 활성 운영 자격 없음, CS 동기화 상태 없음, DB 고정 송신 정책 false, 원격 답변 지원 없음. 한국 판매자 유형과 앱에 일반 메시지 API가 제공되는지 미확정이다.

**구현 순서:** TEM-01에서 판매자 유형·지역·앱 승인·scope·실제 인증·송신 경로를 확보한다. TEM-02에서 반품/환불 목록·상세·기한·주문 참조·상태 이력을 구현한다. TEM-03은 일반 고객 메시지 API를 별도 확인 후 구현한다. 제공되지 않으면 이 범위는 blocked로 남긴다. TEM-04에서 실제 업무 유형별 원격 대조한다.

**완료 증거:** 반품/환불 원격 상태와 웹 작업함 일치, 일반 메시지는 독립 검증, 금전 영향이 있는 승인과 CS 답변을 구분. [Temu 판매자 승인 문서](https://partner.temu.com/documentation?menu_code=38e79b35d2cb463d85619c1c786dd303)의 해당 판매자/지역 조건이 선행한다.

## 3. 상품 등록·배송과 충돌하지 않는 구현 경계

현재 CS 전용 API와 원장은 있지만 `operations.ts`, gateway/worker, 인증·갱신과 일부 DB 함수는 상품 등록과 공유된다. 따라서 ‘완전히 분리됨’으로 판정할 수 없다. 다음 경계를 점진적으로 만든다. 아래 `lib/cs/*`, `app/cs/*`, 메시지 조회 API는 **신설 제안 경로**다.

```text
CS 화면 / 채널별 이력 수집 / 수신 webhook
                ↓
CS 서비스: 계정 권한·최신 고객 턴·대화/답변/이력 상태
                ↓
lib/cs/adapters/<channel>.ts
                ↓
공통 인증·서명·HTTP·gateway 기반
                ↓
채널 API → 원격 결과 확인 → 기존 support_* 원장 → CS 웹 타임라인
```

- 기존 `support_*` 원장을 보완한다. 같은 문의를 따로 저장하는 경쟁 원장을 추가하지 않는다. 필요한 메시지 조회 모델/뷰는 기존 원장의 ID와 연결한다.
- 상품 등록·배송·CS는 업무 데이터, operation 타입, 잠금 키, 재시도 예산과 worker 처리량을 구분한다. 공통 인증을 재사용해도 답변 작업이 상품 상태를 수정하지 않도록 한다.
- 문의 조회/답변 분기부터 어댑터로 추출하고 기존 dispatcher는 호환 호출을 유지한다. 같은 공유 파일은 한 작업 흐름에서만 수정하도록 담당 경계를 고정한다.
- 배송 정보가 CS에 필요하면 주문/운송장 도메인의 검증된 읽기 계약을 참조한다. CS가 배송 수집기를 복제하거나 답변 전송 중 상품 등록·운송장 변경을 실행하지 않는다.
- 채널 연결 배지에 키 저장과 실제 수신·답변·과거 이력 상태를 따로 표시한다. 0건 조회 성공과 동기화 미실행을 구분한다.
- 상품 게시 폭주와 실패가 CS 큐를 막지 않는지 검증한다. 등록/배송 핵심 회귀도 공통 모듈 변경 범위에 맞게 실행한다.

## 4. 과거 CS를 웹사이트에서 보는 완성 경로

단순히 과거 수집 버튼을 추가해서는 끝나지 않는다. **복구→중복 제거→답변 이력 결속→검색/타임라인→원격 대조**를 한 흐름으로 구현한다.

| 단계 | 구현 내용 | 완료 증거 |
|---|---|---|
| 범위 확인 | 채널/계정/유형별 가장 오래된 조회 가능일, 상태, 보관 기간, 공식 export 여부 기록 | 실제 조회 가능한 기간과 복구 불가 기간이 명확함 |
| 이력 작업 | 계정·채널 단독 실행, 날짜 구간·페이지 cursor, 실패 재개, 처리량 제한 | 쿠팡 장애와 무관하게 스마트스토어 진행; 중단 후 이어짐 |
| 원장 저장 | 원격 ID, 고객/판매자 방향, 발생/관측 시각, 원본 출처, 수정/첨부 메타데이터 | push·재수집·발송 echo 중복 0 |
| 기존 답변 | 판매자센터에서 작성한 답변도 별도 메시지로 수집하고 문의에 연결 | 최초 문의와 최종 답변 사이의 대화가 보존됨 |
| 웹 목록 | 채널/계정/유형/기간/상태/검색, cursor 페이지네이션 | 완료된 과거 문의도 전체·완료 필터에서 표시됨 |
| 웹 대화 | 고객→판매자→재문의→앱 답변, 첨부·수정·작성 출처와 전송 상태 표시 | 새로고침과 페이지 이동 후 순서·내용 동일 |
| 정합성 | 범위별 원격 ID·건수와 내부 수집·제외·실패 수 대조 | 조회 가능한 미수집 범위 0, 제외 사유 추적 가능 |

현재 UI의 `selected.originalMessage` 단일 표시를 전체 메시지 타임라인으로 교체한다. 작업 수, 원격 문의 수, 저장 메시지 수를 서로 다른 수치로 보여 준다. 원격 총수가 제공되지 않으면 동일 조회 시점·범위에서 수집한 ID 집합과 모든 페이지 완료 증거를 사용하고, 가능한 판매자센터 표본을 추가 대조한다.

API보다 오래된 자료는 해당 판매자에게 제공되는 공식 export가 있을 때만 가져오기 경로를 추가한다. export 원본 출처·가져온 날짜·원래 작성 시각을 보존하고 원격 ID가 없으면 불확실한 유사 건을 무조건 합치지 않는다. 법정/업무 보관·삭제 규칙을 확정하며, 삭제한 메시지는 재동기화로 되살아나지 않도록 식별자 기반 제외 기록을 유지한다.

## 6. 시험과 최종 수용 기준

### 반드시 확인할 시나리오

- 유형별 실제 신규 문의와 답변완료 과거 문의, 기간 경계·전체 페이지, 외부 답변, 재문의, 지원 첨부·긴 문장·한국어/현지어.
- 동일 이벤트 재전송, 역순 메시지, bootstrap과 새 push 동시 도착, 판매자 답변 echo, 같은 문의 동시 답변.
- 답변 버튼을 누른 뒤 새 고객 메시지가 들어오는 경우, 이미 원격에서 답변된 경우, 판매자/국가/부모 문의 불일치.
- 토큰 만료/교체, 권한 해제, 429/5xx, worker 중단/lease 만료, 페이지 중간 실패, 공급자 수락 이후 응답 유실.
- 잘못된 webhook 서명과 다른 판매자 메시지, 비공개 첨부 접근, 삭제 후 재수집, 대량 검색/페이지 경계.

실제 외부 답변은 허용된 테스트 문의와 정확한 수신자·문구를 정한 후 수행한다. 현재 계획 요청을 고객에게 임의로 메시지를 보내는 권한으로 해석하지 않는다. Sandbox 결과와 운영 결과는 따로 기록하고, 지원되는 경우 통제된 운영 테스트 계정을 사용한다.

### 제안 운영 목표 — BASE-01에서 공급자 제한과 대조하여 확정

| 항목 | 수용 목표 |
|---|---|
| 웹훅 수신 후 내부 저장/화면 반영 | p95 60초 이내; 공급자 전송 지연과 내부 처리 지연 분리 측정 |
| 폴링 문의 감지 | 원격 조회 가능 시각부터 5분 이내 목표; 공급자 한도에 맞는 실제 주기 확정 |
| 수신 정지 감지 | 계획된 성공 주기 2회 초과 시 경고; 문의 0건과 호출 실패 구분 |
| 대화 조회 | 합의한 대량 fixture에서 p95 2초 이내 목표, 페이지 누락/중복 0 |
| 무결성 | 시험 범위 내 수집 누락·중복 답변·다른 계정 저장 0 |
| 불확실한 발송 | 원격 대조 또는 명시된 처리 책임/기한 없이 방치 0; 미조정 건은 최종 완료 차단 |

48시간 문의가 우연히 없었다는 이유로 통과시키지 않는다. 필수 실제 시나리오 증거가 있어야 한다. 토큰 수명이 48시간보다 길면 별도 통제 시험으로 갱신을 확인한다. 48시간 통과는 정의된 시험의 수용 기준이며 미래의 영구 무장애 보장이 아니다.

증거에는 채널/계정/국가/유형, 원격 message ID·reply ID, job/receipt ID, 조회 범위, 실행 SHA·적용 DB 함수 hash, 확인 시각과 결과를 기록한다. 공유 문서에는 고객 본문·개인정보·비밀키를 남기지 않는다. `queued`와 `HTTP 202`는 접수, 공급자 ACK는 수락이며, 원격 반영 확인은 별도 기록한다.

## 7. 배포·롤백 계획

1. 운영 DB 실제 함수 정의·권한·migration history를 먼저 대조한다. 오래된 로컬 파일 전체를 운영에 덮어쓰지 않는다.
2. 기존 원장과 호환되는 migration을 적용하고, API·worker를 배포한 뒤 채널별 기능을 활성화한다. 기존 consumer와 새 스키마의 호환을 시험한다.
3. 실행된 job의 release·route·함수 정의가 예상과 일치하는지 확인한다. 빌드 성공·배포 성공만으로 채널 완료 처리하지 않는다.
4. 이상 시 해당 채널의 신규 enqueue를 중단하고 진행/불확실 작업을 보존한다. 원격 수락 여부를 먼저 대조하며 자동 재발송하지 않는다.
5. 데이터가 쌓인 스키마를 파괴적으로 되돌리지 않는다. 호환 버전 복귀와 영향 범위 격리를 우선한다.
