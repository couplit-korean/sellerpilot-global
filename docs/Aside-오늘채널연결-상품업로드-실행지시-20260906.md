### 파일·브라우저·운영 변경의 소유권

- 시작할 때 `담당 / agent ID / 실제 실행 상태 / 소유 파일 / 채널·상품·탭 / 다음 결과`를 짧게 기록한다. 배정 문구만 쓰고 실제 spawn·작업 전달을 생략하지 않는다. 재시작 시 기존 담당을 확인해 중복 실행을 막는다.
- 총괄은 `app/product-publish-workbench.tsx`, `app/api/admin/channel-operations/route.ts`, 배포·공통 상품 승인·운영 DB 변경·최종 상태 문서를 소유한다. 하위는 명시적으로 배정된 파일만 편집한다. 같은 파일이 필요하면 패치 제안으로 넘기고 소유권을 이전받기 전에는 수정하지 않는다.
- 가능하면 하위 코드 작업은 격리된 작업 디렉터리/브랜치에서 수행한다. 같은 체크아웃이면 파일 소유권을 지키고 하위의 commit·stash·reset·전체 포맷으로 다른 변경을 섞지 않는다. 총괄은 필요한 변경만 선별 통합한다.
- 공통 배포·운영 SQL·승인본 교체·재고 변경은 총괄 한 곳에서만 수행한다. 첫 등록과 관련 없는 하위 변경을 첫 릴리스에 한꺼번에 넣지 않는다. 하위 완료를 전부 기다리는 통합 장벽을 만들지 않는다.
- 다른 채널의 실제 등록·수정·OAuth도 기존 권한과 claim/lock 계약이 허용하고 총괄이 해당 채널·상품·작업 소유자를 단독 배정한 경우에는 동시에 실행할 수 있다. 각 job/attempt·원격 ID·재조회를 분리한다. 같은 상품의 공통 잠금이 이를 막으면 준비·검증은 병렬 유지하고 외부 쓰기만 정상 순서로 실행한다. 잠금을 우회하지 않는다.
- 동일 브라우저 탭을 둘이 조작하지 않는다. 각 담당의 탭을 배정하며 공유 로그인 세션을 로그아웃·전환하지 않는다. 짧은 OAuth 세션을 맡은 담당은 완료·만료까지 그 세션에 집중한다.
- 운영 DB·API 읽기는 현재 제한 안에서 필요한 범위만 수행한다. 총괄이 이미 확보한 마스킹 메타데이터를 공유해 같은 조회를 여러 명이 반복하지 않는다. 전체 빌드·타입 검사는 같은 작업 디렉터리에서 동시에 실행하지 않는다.
- 하위는 결과를 `변경 파일·검증·실제 외부 결과·차단·다음 행동`으로 전달하고, 비밀 없는 증거를 지속되는 비공개 위치에 보관한다. 공통 상태 문서를 동시에 덮어쓰지 않는다. 총괄은 첫 채널 성과 즉시 보고하고 다른 담당은 계속 작업한다.

- 준비된 기존 상품의 연결, 정식 가격·배송·정책 확인, 실제 등록·수정, 원격 재조회까지 실행한다. 이에 필요한 최소 코드 수정과 검증된 운영 반영도 진행한다.

## 2-1. 누락·중복·재작업 방지

공용 원장을 작업 배정과 완료 판정의 단일 기준으로 쓴다. 총괄만 원장을 갱신하고 하위는 task ID별 결과를 전달한다. 시작 때 원장의 전체 분야가 배정됐는지 확인하되 모든 분야의 조사를 첫 등록 전에 실행하지 않는다.

1. **착수 전:** 동일 목표·상품·채널·operation·파일의 기존 RUNNING/READY/DONE, 실제 에이전트·job·원격 ID를 확인한다. 중복 담당을 만들지 않는다. P0 등록 행과 채널 행은 같은 job을 참조한다.
2. **완료 재사용:** 동일 소스 SHA·승인 버전·계약의 완료 증거가 있으면 재구현·재생성·재배포·같은 테스트 반복을 하지 않는다. 현재 운영 값은 필요한 항목만 재조회한다. 변경·증거 공백이 있으면 같은 task ID에 사유와 최소 재검증 범위를 먼저 기록한다.
3. **쓰기 전:** 담당·현재 승인·필수값·claim/lock·중복 원격 상품을 확인한다. timeout/202/응답 유실이면 기존 job과 원격 결과를 조회한다. 새 멱등키·새 create로 미결 결과를 우회하지 않는다.
4. **완료 처리:** 하위의 종료 알림만으로 완료하지 않는다. 변경 파일·정확한 검증 판본·결과·외부 재조회·남은 조건을 확인한다. 준비/배포/등록/판매 상태를 분리한다.
5. **누락 점검:** 진행 보고 시 무담당 TODO, 실행자 없는 RUNNING, 증거 없는 DONE, 중복 파일·탭·채널 소유, 필요한 사용자 입력이 미요청된 BLOCKED를 확인한다. 마감 때 8채널·상세·CS·재고·주문·배송·DB·배포 모두 상태와 다음 행동을 남긴다.

이 규칙은 오류를 발견하고 복구하기 위한 것이다. “누락 없음/완료” 표기는 실제 원장 대조와 증거가 있을 때만 사용한다.

보호 미추적 `supabase/migrations/20260903150000_unblock_shopee_second_oauth_deadlock.sql`은 **읽기·수정·삭제·스테이징·커밋·테스트 입력·운영 적용에서 제외**한다.

## 6. 검증된 최소 변경의 운영 반영

- 운영에 수정이 이미 있으면 재배포하지 않는다. 없으면 변경 범위·검증 결과를 남기고 기존 검증된 배포 절차로 반영한다.
- 실제 배포 SHA, `SELLERPILOT_RELEASE_SHA`, DB active release, 게이트·어댑터·재조회 증명을 새 릴리스 기준으로 확인한다. 상태를 임의 통과 처리하지 않는다.
- Ready 이후 실제 관리자 화면에서 대상 상품 승인 상세와 게시 진입을 확인한다. 무작업 canary를 상품 게시 성공으로 계산하지 않는다.
- 필요한 파일만 비밀 검사 후 `origin`·`couplit`의 `integration-aside`에 정상 fast-forward로 동기화한다. main 변경, force push, 계정 초기화, 키 일괄 교체, 유료 Static IP 구매는 하지 않는다.
- SQL이 실제로 필요하면 현재 정의·이력·권한을 검토하고 신규 변경만 원자적으로 적용한 뒤 독립 조회한다. 이미 적용된 070000이나 과거 SQL을 재실행하지 않는다.

## 7. 채널별 실행 순서

**총괄의 P0 후보는 스마트스토어·쿠팡이며, 먼저 선택한 한 채널의 등록·재조회까지 끝낸다.** 두 번째 채널 후보에 Qoo10을 포함하되 기존 ID update와 신규 create를 구분한다. 다른 채널은 각 하위가 즉시 병렬 준비·검증하고, 권한과 작업 소유권이 확보되면 실제 실행도 진행한다.

| 채널 | 바로 할 일 | 쓰기와 완료 확인 |
|---|---|---|
| 스마트스토어 | 토큰·판매자·읽기, 카테고리·이미지·본문·가격·배송 검증 | 기존 원격 상품 검색 후 create/update 선택, 원격 상품과 새 상세 재조회 |
| 쿠팡 | 복구·읽기 성공 이력에서 출발해 현재 쓰기 권한·필수값 확인 | 오래된 경고만으로 차단하지 않음. 중복 검색 후 등록/수정, 등록·판매/심사 상태 구분 |
| Qoo10 | 1217536689와 원장·복구 증거 확인 | 기존 ID update, 새 이미지·본문·가격·재고·배송 확인. 새 create 금지 |

| 11번가 | 9598600918 GET, 이메일 인증, 배송비 3,000원 공식 계약 | 무료배송 우회 금지. 실제 배송 조건 검증 후 기존 ID 수정·재조회 |

OAuth는 로그인·브라우저·실행기가 준비된 뒤 시작한다. 세션이 열린 동안 보고서 작성이나 다른 조사로 이탈하지 않는다. 만료 코드·세션은 재사용하지 않는다.

멀티에이전트 담당표에 따라 실제로 동시에 작업한다. 총괄은 첫 채널 완료를 다른 담당의 종료까지 기다리지 않고, 하위는 총괄의 첫 성공을 기다리며 쉬지 않는다. 파일·운영 변경·브라우저 소유권과 기존 claim/lock 계약을 유지한다.

SellerPilot을 거치지 않은 판매자센터 수동 등록을 자동화 연결 성공으로 대체하지 않는다. 별도 수동 대안은 사용자에게 정확히 구분한다.

## 8. 당일 시간 운영

작성 시점은 약 18시 KST, 당일 기한까지 약 6시간이다. 시작 시 실제 시계로 남은 시간을 다시 계산한다. 아래는 작업 예산이며 성공 보증이나 검증 생략 허가가 아니다.

1. 첫 10분: 스마트스토어·쿠팡 중 첫 등록 채널 하나 선택. 전체 채널 조사는 하지 않는다.
2. 즉시: 선택한 채널의 필수 수정·배포 확인과 실제 등록 실행. 시작 후 60분 안에 첫 등록·원격 재조회 확보를 목표로 삼고, 필요한 검증을 생략하지 않는다.
3. 첫 성공 즉시: 원격 ID·등록 내용·판매/심사 상태·실제 사용자 화면 경로를 먼저 보고한다. 두 번째 채널을 이어서 처리해 시작 후 2시간 안에 2개 확보를 목표로 한다.
4. 같은 시간 동안: 하위는 다른 채널과 잔여 개발을 병렬 수행한다. 총괄은 P0 결과 확보 후 준비된 결과를 차례로 검증·반영한다. 23:59 보고에서 P0 성과·전체 채널 확대·병렬 개발 완료를 구분한다.

같은 원인에서 새 증거가 20분 이상 늘지 않으면 사실·시도·필요 증거를 짧게 남기고 준비된 다른 채널로 전환한다. 불확실한 쓰기는 재전송 대신 기존 job·원격 상태를 조회한다. 공식 재시도 간격·rate limit을 지킨다.

첫 성공 전에는 15분마다 선택 채널·현재 실제 단계·막는 원인 한 가지·다음 동작만 짧게 알린다. 첫 성공 즉시 증거를 보고하고, 두 번째 성공 후 전체 결과표를 갱신한다. 60분 목표를 넘기면 원인과 다음 실행을 알리되 종료하거나 성공 기준을 낮추지 않는다.

## 9. 완료 판정과 증거

상태를 분리한다: `미시도 → 연결 읽기 확인 → 게시 조건 충족 → 요청 접수 → 공급자 등록 확인 → 새 상세 원격 재조회 → 판매 화면 확인`.

- 연결: 의도한 현재 판매자/숍·권한으로 실제 읽기 성공. 키 저장·로그인·과거 진단은 별도.
- 업로드 확인: 원격 ID 생성/수정과 새 상세 v2 이미지·본문의 원격 재조회 확인.
- **P0-1 완료:** 신규 등록 요청의 성공과 원격 상품 ID·내용 재조회가 확인되어야 한다. 기존 상품 update만 성공했으면 update 가능으로 보고하고 create 가능 검증은 계속한다. 다른 사람이 이미 완료한 동일 대상의 최근 create 증거가 있으면 재등록 대신 해당 증거와 현재 상태를 확인한다.
- 실제 운영 화면에서 사용자가 어디로 들어가 어떤 상품을 선택해 어느 채널로 등록하는지 경로를 제시한다. 서버 호출만 성공하고 UI가 여전히 막히면 “화면에서 즉시 등록 가능”을 완료로 보고하지 않는다. 기능을 증명하려고 같은 상품을 두 번 등록하지 않는다.
- 판매 가능 확인: 판매 가능 상태와 구매자 화면 확인. 심사 중·draft·비공개는 별도.
- HTTP 202/inProgress, enqueue, 공급자 호출 시작, 테스트 통과, 배포 Ready를 위 완료로 세지 않는다.
- 가격·통화·재고·배송비·제목·현지어 본문·이미지·ID를 대조한다. 미확인 값은 미확인으로 남긴다. 승인된 ko/ja/en 외 언어가 필요하면 정식 현지화 경로와 검수를 사용한다.

증거는 `.local/evidence/2026-09-06-aside-listing/`처럼 지속되는 비공개 위치에 저장한다. ignore·권한을 확인하고 비밀값·signed URL·고객 원문을 기록하지 않는다. 공개 Git에는 마스킹 요약만 넣는다. 종료 전 실제 파일 존재를 확인한다.

## 10. 마감과 후속 범위

실제 결과를 `docs/현재상태.md` 맨 위에 먼저 갱신하고 운영 진행·진행률 비교 문서의 최신 요약을 맞춘다. 과거 기록은 날짜와 함께 보존한다. 필요한 파일만 검사·커밋·정상 push하고 두 integration SHA를 확인한다.

CS·재고·주문·배송·반복 자동 상세·DB 복원 관련 코드와 격리 검증은 하위가 이미 병렬 진행한다. 총괄은 첫 게시 후 준비된 변경의 운영 반영과 실제 흐름 검증을 이어간다. 이 전체를 첫 게시의 일괄 선행조건으로 묶지 않는다. 실제 고객 발송·출고 대상과 내용은 해당 단계에서 명시적으로 확정한다.

시작 응답은 경로·HEAD·첫 실행 대상·실제 병렬 담당만 짧게 말하고 바로 실행한다. 계획만 제시하거나 “계속할까요?”로 끝내지 않는다. 실제로 필요한 인증·가격 선택만 정확히 요청하고 독립 작업은 계속한다.
