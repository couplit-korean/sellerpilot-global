## 9. 재개 시 병렬 배치와 파일 소유권

이 작업의 최대 슬롯은 총괄 포함 4개다. 중지 시 2개 하위 담당은 작업을 멈췄고, 나머지 기존 검증 담당은 사용량 한도로 중단돼 있다. **4개가 지금 정상 가동 중이라고 보고하지 않는다.** 재개 시 가용성을 확인하고 안 되는 슬롯은 총괄이 흡수한다. 자동 사용량 초기화/유료 자원 구매는 하지 않는다.

### 1차 배치 — 스마트스토어 정상 완료 + 쿠팡 준비

| 담당 | 독립 범위 | 쓰기 소유권 | 의존/보고 |
|---|---|---|---|
| 총괄 | 운영 설정 정렬, 증거 대조, 통합, SQL 적용, 실제 읽기/전송 조정 | 운영 DB/배포/게이트 및 실행 원장 | 다른 담당은 운영 상태를 바꾸지 않음 |
| A | 175400 문법/DB 계약/실패 회귀 | 175400 SQL + 관련 DB 테스트 | 최종 SHA/test 결과 제출 |
| B | A의 독립 리뷰, strict API/일반경로 회귀 확인 | 기본 읽기 전용; 수정 필요 시 파일 인계 | P0/P1와 완료 기준 확인; A 파일 직접 동시 수정 안 함 |
| C(가용 시) | 쿠팡 출고조건 증거/초안·payload 점검 | 쿠팡 전용 범위만, 공통 상품 실제 저장은 총괄과 순서 합의 | 미확정 사실 목록/준비된 요청 제출 |

### 2차 배치 — 첫 1~2채널 검증 이후

총괄은 결과 통합과 실제 전송을 맡는다. A는 11번가 snapshot/유료배송, B는 Qoo10/Shopee의 기존 계보 복구, C는 eBay 정책/가격을 맡는다. 한 담당이 맡은 채널을 끝내면 다음 채널로 이동한다. Lazada/Temu는 외부 승인 대기 항목만 분리 점검한다. 독립 이미지/CS 작업에는 기존 담당이 있으므로 같은 파일을 맡는 새 작업을 만들지 않는다.

공통 파일 `lib/channels/operations.ts`, worker, 완료 API, 공통 입력 컴포넌트, migration dispatcher를 두 사람이 동시에 고치지 않는다. 변경이 필요하면 원장에 소유권을 넘긴 뒤 수정한다. 동일 상품의 채널 초안 저장도 버전 충돌을 피하도록 조정한다.

## 10. 누락·반복·중복 방지 규칙

1. 재개 전에 HEAD/dirty files/최신 문서/실제 runtime/DB history/미종료 job을 읽는다. 오래된 계획의 명령부터 실행하지 않는다.
2. 모든 작업은 위 ID로 기록한다. 상태는 `미착수 → 진행 → 로컬 검증 → 운영 반영 → 원격 검증 → 완료`이며 실패/외부 대기는 별도 표시한다.
3. 완료 기록에 검증 시각·SHA·migration hash·job/remote ID·다음 미완료 항목을 남긴다. 코드 테스트와 운영 증거를 한 칸에 섞지 않는다.
4. `reconciliation_required` 또는 응답 불명은 **재조회 대상**이다. 동일 CREATE/PUT을 무조건 다시 보내지 않는다.
5. SmartStore `13688607602/13749310594`, Qoo10 `1217536689`, 11번가 `9598600918`은 기존 연결/UPDATE로 이어간다.
6. 기존 source·repair·permit·completion·raw receipt를 감사 원본으로 보존한다. 새로운 검증 영수증으로 상태를 설명한다.
7. SQL은 실제 이력의 version/name/hash 대조 후 미적용 최종 원문만 적용한다. 다른 담당의 CS SQL/보호 SQL을 함께 실행하지 않는다.
8. 테스트는 변경 관련 검사와 의미 있는 실패 회귀를 수행한다. 새 변화나 오류 없이 이미 통과한 전체 빌드/모든 테스트를 반복하지 않는다.
9. Chrome 사용 전 프로필 목록 확인: 쇼핑 CHANGHEE `k931103@gmail.com`, Vercel/Supabase JEONGHUN `couplit.official@gmail.com`. 브라우저 ID는 매번 재확인한다.
10. 원장에 `요청한 것/확인한 것/아직 확인 못한 것`을 구분하고 비밀값·고객 원문은 기록하지 않는다.
