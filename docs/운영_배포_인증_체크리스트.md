# SellerPilot 운영 배포·인증 체크리스트

이 문서는 코드로 완료할 수 없는 계정 승인 지점만 모은 운영 체크리스트다. 비밀번호, API Key, OAuth Code, Access Token 원문은 문서·Git·터미널 로그에 기록하지 않는다.

## 1. Supabase 프로젝트 승인과 마이그레이션

Couplit 운영 프로젝트 소유 계정으로 Supabase CLI 또는 Dashboard에 로그인한 다음, 현재 연결 대상의 project ref를 운영 환경변수와 대조한다. 다른 프로젝트에 연결된 상태에서는 적용하지 않는다. `supabase/migrations`를 이름순으로 확인하고 아직 적용되지 않은 파일만 forward 방식으로 적용한다. 이미 적용된 migration 파일은 수정하지 않는다.

```bash
supabase login
supabase link --project-ref <PROJECT_REF>
supabase db push
```

이번 릴리스는 운영 DB에 아직 적용되지 않은 forward migration을 파일명 순서대로 모두 적용해 최소 `20260830204000_allow_fresh_lazada_oauth_past_oauth_reconciliation.sql`까지 도달해야 한다. `20260828210000_non_cs_release_integrity.sql`만 적용한 상태는 완료가 아니다. 최신 gate가 적용되고 Shopee static-egress 상태가 기본 `false`이며 generic/persistent worker 우회가 닫힌 것을 확인하기 전에는 gateway와 internal schedule을 활성화하지 않는다.

Lazada OAuth 릴리스는 신규 작업을 수락하지 않는 동일 후보 아티팩트로 no-work canary를 먼저 확인한다. 다음에 gateway와 internal schedule을 일시 중지하고, `channel_gateway_jobs`의 `status = 'running'`인 작업과 유효한 gateway lease가 모두 0건이 될 때까지 drain을 기다린다. 그 다음에 동일 아티팩트를 승격하고 `20260830203000_record_lazada_oauth_provider_call_boundary.sql`, `20260830204000_allow_fresh_lazada_oauth_past_oauth_reconciliation.sql` 순서로 forward migration을 적용한다. marker RPC와 fresh-authorization recovery function을 확인한 후에만 canary를 활성화하고 schedule을 재개한다. `20260830203000`이 없는 DB에서는 신규 Lazada OAuth 코드가 provider 호출까지 진행하지 않도록 한다.

```sql
select count(*) as running_gateway_leases
from sellerpilot_private.channel_gateway_jobs
where status = 'running'
   or (lease_expires_at is not null and lease_expires_at > clock_timestamp());
-- 예상: 0
```

첫 앱 관리자는 Supabase Auth 사용자 생성 후 SQL Editor에서 명시적으로 승인한다.

```sql
insert into sellerpilot_private.admin_users (user_id, display_name)
select id, 'SellerPilot Admin'
from auth.users
where lower(email) = lower('<APP_ADMIN_EMAIL>')
on conflict (user_id) do update set display_name = excluded.display_name;
```

완료 증거:

- `supabase_migrations.schema_migrations`에 `20260830204000`까지 모든 미적용 version이 파일명 순서대로 한 번씩 기록됨
- `public.sellerpilot_service_mark_lazada_oauth_provider_call_started` RPC와 `sellerpilot_private.safe_lazada_oauth_exchange_reauthorization_blocker`, `sellerpilot_private.safe_lazada_oauth_refresh_blocker` function이 존재하며 public/anon/authenticated 실행 권한은 없음
- 동일 후보 no-work canary 통과 → gateway/internal schedule inactive → `running_gateway_leases = 0` → 동일 artifact 승격 → 203000·204000 적용 순서를 기록함
- PGlite 전체 migration 테스트와 운영 프로젝트 Advisor 확인 통과
- 앱 로그인 후 `운영 DB · Supabase 관리자 데이터` 배지 표시
- 비관리자 계정은 대시보드 대신 권한 안내 화면 표시
- 운영 상품·주문·문의 데이터는 QA 편의를 이유로 생성하거나 삭제하지 않음

## 2. Vercel 환경변수와 정리 작업

Couplit 소유 Vercel 프로젝트의 Preview와 Production에 아래 값이 있어야 한다.

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- `SUPABASE_SECRET_KEY`
- `SELLERPILOT_AI_WORKER_TOKEN` — Supabase의 활성 `ai` 범위 토큰과 일치하는 Vercel sensitive 값. 브라우저·로그·문서에 원문을 표시하지 않음
- `SELLERPILOT_RELEASE_SHA` — 후보 배포와 동일한 40자리 Git commit SHA
- `CRON_SECRET` — 새 무작위 값, Production 전용 관리 권장
- `SELLERPILOT_SERVERLESS_STATIC_EGRESS_CHANNELS` — **Vercel Static IP와 판매채널 허용 목록이 실제로 일치한다고 검증된 채널만** 쉼표로 설정

Vercel AI Gateway의 기본 인증은 요청마다 Vercel이 제공하는 OIDC다. `VERCEL_OIDC_TOKEN`을 환경변수나 파일에 직접 만들거나 복사하지 않는다. 계정 정책상 OIDC를 쓸 수 없는 경우에만 서버 전용 `AI_GATEWAY_API_KEY`를 대체 인증으로 설정하고, 둘 다 `NEXT_PUBLIC_` 접두사를 사용하지 않는다.

`서버 사용량` 화면까지 사용할 경우에만 Vercel·Supabase Management API의 읽기 전용 환경변수를 추가한다. 값이 없으면 화면은 사용량을 추정하지 않고 `연결정보 없음`으로 표시한다.

- `VERCEL_ACCESS_TOKEN`, `VERCEL_TEAM_ID`
- `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_ORGANIZATION_SLUG`

동일상품 가격 공급자를 사용할 경우 필요한 서버 전용 연결 이름은 아래와 같다. 지원되는 채널 자격증명은 Supabase Vault에서 대신 읽을 수 있지만, 운영에서 실제로 연결되지 않은 공급자는 화면에 `미연결`로 남겨야 한다.

- `NAVER_SEARCH_CLIENT_ID`, `NAVER_SEARCH_CLIENT_SECRET`
- `ELEVENST_OPEN_API_KEY`
- `EBAY_BROWSE_CLIENT_ID`, `EBAY_BROWSE_CLIENT_SECRET`
- `BRAVE_SEARCH_API_KEY`

Vercel Cron은 0건으로 유지한다. 상품조사·주문 동기화·동일상품 가격·카카오 알림은 Supabase `pg_cron`/`pg_net`이 5분 간격의 서로 다른 분에 실행하고 maintenance도 Supabase가 일 1회 실행한다. 문의 동기화는 분 단위 channel gateway drain만 소유해 5분 주문 route와 중복 enqueue하지 않는다. Supabase Vault에는 raw `CRON_SECRET`이 아니라 HMAC 파생 bearer만 저장한다. 완료된 AI·판매채널 이미지와 직접 식별 데이터는 30일 보관 원장에 따라 정리한다. 파생 bearer가 없거나 다르면 401/503으로 거부해야 정상이다.

Vercel Static IP는 별도 유료 기능이다. 사용자 승인 없이 구매하거나 켜지 않는다. 이미 활성화된 경우에만 실제 송신 IP, 쿠팡·스마트스토어·11번가·Temu·Shopee 허용 목록, Supabase 고정 egress 정책을 대조한 뒤 `SELLERPILOT_SERVERLESS_STATIC_EGRESS_CHANNELS`에 해당 채널을 추가한다. Shopee는 OAuth 토큰 교환도 같은 게이트를 통과해야 하며, 플래그만 먼저 켜서는 안 된다.

## 3. Qoo10 인증 게이트

`API 키 · 인증` 화면에서만 Qoo10 Seller ID, Certification Key, 승인된 읽기 검사 상품번호를 입력한다. 저장 즉시 원문은 Supabase Vault로 이동한다. 연결 검사는 Qoo10 공식 상품 상세 읽기 API의 성공 응답을 확인하며, 테스트상품 쓰기는 사용자 승인 범위가 확정되기 전 실행하지 않는다.

## 4. Lazada 인증 게이트

`API 키 · 인증`에 App Key·App Secret을 입력하면 앱이 일회성 OAuth state를 HttpOnly 쿠키에 저장하고 Lazada 승인 화면으로 이동한다. 복귀 후 code는 즉시 URL에서 제거하고 state를 검증한 뒤 서버에서 토큰으로 교환해 Vault로 옮긴다. 단, 실제 토큰 교환과 판매자 읽기 검사는 개발자 콘솔 White IP와 동일한 고정 공인 송신 IP가 필요하다.

## 5. Shopee 인증 게이트

`API 키 · 인증`에 Live Partner ID·Partner Key를 입력하면 최신 `https://open.shopee.com/auth` 승인 링크로 이동한다. Main account 콜백의 code·main_account_id·state를 검증하고 반환된 8개 shop_id별 Access/Refresh Token을 Vault에 분리 저장한다. API 실행 검수 JSON의 `shopId`로 국가 숍을 선택하며 해당 숍 토큰만 만료 전에 갱신한다.

## 6. 쿠팡·네이버 인증 게이트

- 쿠팡: WING 로그인 → 우측 판매자명 → 추가판매정보 → 비밀번호 재확인 → OpenAPI Key 확인/발급 순서다. 키는 180일 유효하고 만료 14일 전부터 재발급할 수 있다. Vendor ID·Access Key·Secret Key를 운영 화면에 한 번만 입력한 뒤 등록상품 목록 1건 읽기를 통과시킨다.
- 네이버: 스마트스토어 통합매니저 계정으로 Commerce API센터 개발업체 계정을 생성하고 내 스토어 애플리케이션을 등록한다. 판매자 상품·주문 API는 `SELLER` 유형과 판매자 UID(`account_id`)를 사용하며 토큰은 180분이다. `GW.AUTHN` 401이면 서버가 토큰을 한 번 재발급하고 동일 요청을 재시도한다.

## 7. Vercel 서버 AI 스튜디오

Production 상품 분석·이미지 제작은 Vercel Node 런타임만 사용한다. Mac LaunchAgent, 로컬 Codex CLI, `npm run ai:worker:install*`은 운영 선행조건이나 장애 시 자동 대체 경로가 아니다. 해당 스크립트는 격리된 로컬 개발·이전 호환 검증에만 사용한다.

1. 후보 배포의 Vercel sensitive environment에 `SELLERPILOT_AI_WORKER_TOKEN`을 저장하고, Supabase에 활성화된 `ai` 범위 토큰 지문과 일치하는지 확인한다. 원문은 브라우저에서 발급·조회·복사하지 않는다.
2. Vercel 요청 범위에서 AI Gateway OIDC 인증을 확인한다. `VERCEL_OIDC_TOKEN`은 Vercel이 자동 제공하므로 직접 저장하지 않는다.
3. 관리자 로그인 후 `API 키 · 인증`의 **서버 AI 스튜디오 런타임**에서 `Vercel Node + OIDC`, `Supabase 비공개 큐`, 서버 토큰 일치 상태를 먼저 확인한다. 이어 **AI Gateway 실제 호출 점검**을 통과한 짧은 서명 검증 상태가 표시되어야만 상품 AI 실행 가능으로 판정한다. 마지막 Mac heartbeat나 구성 감지만 운영 준비 판정에 사용하지 않는다.
4. Supabase의 상품조사 일정이 같은 release canary를 통과해 활성화됐는지 확인한다. 이 5분 일정은 응답 직후 `after()` 실행이 끊긴 경우 상품 스튜디오 큐를 먼저 복구한다.
5. 대표사진을 포함한 승인된 테스트 상품 1건을 웹 또는 모바일에서 요청해 16개 이미지, 분석 JSON, 26개국 현지화 결과가 terminal success로 저장되는지 확인한다.

### 서버 AI 토큰 불일치·만료 복구

서버 AI 런타임 카드의 `서버 토큰 불일치`는 Supabase에 만료되지 않은 활성 `ai` 토큰이 있지만 Vercel의 `SELLERPILOT_AI_WORKER_TOKEN` 지문과 다르다는 뜻이다. `활성 AI 토큰 없음·만료`는 Supabase 상태 조회가 만료되지 않은 활성 `ai` 토큰을 반환하지 않았다는 뜻이다. `토큰 상태 조회 실패`나 `서버 구성 확인 필요`는 만료의 증거가 아니므로 토큰부터 교체하지 않는다. 5분 큐 복구 일정은 끊긴 `after()` 실행만 보정하며 토큰 불일치나 만료를 자동 복구하지 않는다.

1. 새 상품 AI 요청은 readiness gate가 차단한 상태로 둔다. 카드의 실행·대기 수와 운영 원장의 lease를 확인한다. `running > 0`이거나 소유권이 확정되지 않은 작업이 있으면 토큰 교체와 작업 재시도를 중단하고 먼저 terminal 상태 또는 lease 만료·회수 결과를 확인한다.
2. 불일치가 Vercel 환경변수 또는 배포 변경 직후 시작됐고 현재 Supabase 활성 지문과 일치했던 마지막 정상 배포를 정확히 식별할 수 있으면 원문을 꺼내지 말고 그 배포를 복원한다. 복원 후 카드가 일치 상태로 돌아오면 DB를 바꾸지 않는다. 정상 배포를 증명할 수 없으면 값을 추측하거나 이전 원문을 조회하지 말고 다음 server-only 교체 절차로 진행한다.
3. 승인된 원문을 복구할 수 없거나 활성 토큰이 만료됐다면 승인된 운영 셸에서 32바이트 이상의 난수로 `spw_` 토큰을 한 번만 생성한다. 원문은 권한 `0600`의 임시 파일 또는 동등한 비노출 입력 채널에만 보관하고 stdout·로그·Git·브라우저로 출력하지 않는다. 같은 셸에서 SHA-256 해시와 대문자 12자리 지문을 계산한다.
4. 새 원문은 정확한 Vercel 프로젝트의 `SELLERPILOT_AI_WORKER_TOKEN` sensitive environment에 CLI 표준입력으로만 준비한다. Supabase에는 원문을 보내지 않고 해시·지문·`ai` 범위·만료일만 사용한다. 웹의 작업자 토큰 발급 응답이나 과거 로컬 설치 UI를 서버 AI 복구 수단으로 사용하지 않는다.
5. 실행 중 lease가 0임을 다시 확인한 변경 창에서 동일 release를 새 Vercel 환경변수로 재배포한다. 이어 정확한 운영 Supabase의 제한된 database-owner 트랜잭션으로 기존 활성 `ai` 레코드를 폐기하고, 검증된 관리자 UUID로 새 해시·지문·만료 레코드 및 `token_revoked`·`token_issued` 감사를 함께 기록한다. 한 단계라도 실패하면 트랜잭션을 롤백하고 readiness가 차단된 상태를 유지한다.
6. 카드가 `서버 구성 감지`와 `Vercel 서버 토큰과 활성 AI 토큰 일치`를 표시하고 **AI Gateway 실호출 확인**까지 통과한 뒤에만 임시 원문을 안전하게 폐기한다. 승인된 테스트 상품 1건으로 claim·heartbeat·terminal completion receipt를 확인하고, 그 전에는 실패 작업을 다시 실행하지 않는다.

이 절차는 운영자에 의한 외부 Vercel·Supabase 변경 승인이 있을 때만 실행한다. SellerPilot 웹은 토큰 원문을 발급·조회·복사하거나 교체 mutation을 호출하지 않는다.

모바일·웹 사용자는 SellerPilot API만 호출한다. 상품 AI, 판매채널 작업, 주기 실행은 모두 Vercel·Supabase 경로에서 처리하며 로컬 프로세스 실행 여부로 운영 완료를 판정하지 않는다.

후보 배포는 `pnpm deploy:vercel:candidate`로만 생성한다. 이 명령은 깨끗한 checkout의 정확한 40자리 HEAD를 `SELLERPILOT_RELEASE_SHA` build/runtime override와 배포 metadata에 함께 넣고, `--skip-domain`으로 공개 Production alias 승격을 차단한다. Vercel이 프로젝트 내부 후보 alias를 붙일 수는 있지만 검증 전에 `sellerpilot-global.vercel.app`로 promote하지 않는다. 프로젝트에 저장된 이전 `SELLERPILOT_RELEASE_SHA` 값을 믿거나 일반 `vercel deploy --prod`로 후보를 만들지 않는다. 출력된 정확한 SellerPilot 후보 URL에서 보호된 후보 canary API를 먼저 통과시켜 runtime SHA까지 같음을 증명한다. 그 뒤 migration 전에 기존 분 단위 cron을 중지하고 status가 `active: false`인지 확인한다. source metadata와 runtime canary가 같은 SHA인 검증 후보만 Production으로 승격하며 Vercel cron inventory가 0건이 아니면 중단한다. 명령은 비밀값을 출력하지 않으며 정확한 운영 Supabase host가 아니면 중단한다.

고유 배포 URL은 Deployment Protection이 꺼지면 공개될 수 있으므로 URL 형식, `VERCEL_URL`, 프로젝트 ID, release SHA는 인증으로 취급하지 않는다. 후보 canary API는 `vercel curl`이 자동으로 제공하는 프로젝트 보호 우회 토큰을 배포 내부의 `VERCEL_AUTOMATION_BYPASS_SECRET`과 상수시간 비교한 뒤에만 열린다. 일반 SellerPilot 관리자 세션은 이 경로를 열 수 없다. 서버는 배포 내부의 `CRON_SECRET`으로 HMAC bearer를 파생하고 짧은 수명의 Vercel OIDC self-access로 정확한 고유 배포의 gateway 1개와 schedule 5개를 호출한다. 응답은 `release`, `claimed: 0`, `processed: 0`, `executed: false`만 포함하며 CRON 원문, 파생 bearer, 보호 토큰, OIDC 토큰은 응답·명령·로그에 기록하지 않는다. 자동화 보호 비밀이 후보 빌드에 포함되지 않았거나 `vercel curl` 토큰과 일치하지 않으면 HTTP 401로 중단하고 우회하지 않는다.

```bash
pnpm deploy:vercel:candidate
pnpm dlx vercel@59.10.0 curl /api/admin/serverless-runtime-release --deployment <후보-URL> -X POST -H 'content-type: application/json' --data '{"action":"candidate_canary"}'
```

```bash
pnpm gateway:serverless:configure --deactivate --status
```

그 다음 migration 적용과 운영 배포를 마친 뒤 아래 순서를 실행한다.

```bash
pnpm gateway:serverless:configure --bootstrap
SELLERPILOT_EXPECTED_RELEASE=<40자리-커밋-SHA> pnpm gateway:serverless:configure --canary --activate --status
```

gateway 및 상품조사·주문·가격·카카오·maintenance route canary는 작업을 claim하거나 외부 채널/카카오/정리 작업을 호출하지 않는다. 같은 release의 여섯 canary가 모두 성공하고 10분 canary receipt가 완료되며 queued/running 외부 mutation이 0건인 경우에만 Supabase의 gateway wake와 다섯 internal schedule을 함께 활성화한다.

## 8. Production 승격 기준

- Preview에서 로그인 → 상품 AI 생성 → 상품 원장 반영 → 마진 저장 → 진행/히스토리 → 상품 수정 흐름 통과
- Production에서 gateway·상품조사·channel-sync·competitor·Kakao no-work canary, route별 scheduler status, 일 1회 maintenance 인증 확인
- 390px iPhone, 344/330px Galaxy Fold 커버, 데스크톱에서 동일 핵심 흐름 통과
- Qoo10 읽기 API 통과
- Shopee 8개 숍 토큰 교환과 각 숍 `get_shop_info` 읽기 통과
- Lazada OAuth와 안전한 읽기 진단 통과
- 고정 egress 5개 채널(쿠팡·스마트스토어·11번가·Temu·Shopee)은 Vercel Static IP·판매채널 허용 목록·DB 정책·요청 attestation이 모두 확인된 경우에만 `지원`으로 표시
- Vercel Runtime Log에 비밀 원문이나 고객 개인정보가 남지 않음
- 외부 상품 게시·배송 확정·고객 답변은 사용자가 정확히 승인한 테스트 대상이 있을 때만 실행

위 증거가 없는 배포는 Preview로만 유지하고 Production 별칭으로 승격하지 않는다.

## 9. 계정·브라우저 인증 게이트

- Vercel·Supabase 브라우저 검증은 작업 직전에 Chrome 인스턴스를 다시 조회하고 `profileName: JEONGHUN`인 정확한 인스턴스에서만 수행한다.
- 판매채널·개발자센터 검증은 같은 방식으로 `profileName: CHANGHEE`에서만 수행한다.
- 필요한 프로필이 연결되지 않았으면 다른 프로필이나 전체 화면 Computer Use로 우회하지 않는다.
- CLI를 사용할 때도 대상 Vercel 프로젝트와 Supabase project ref를 배포 직전에 다시 읽고 운영값과 일치하지 않으면 중단한다.
