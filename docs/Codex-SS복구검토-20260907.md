## 필요한 최소 exact 복구 계약 설계 — 미구현·미적용

### A. 원본 시각 정합성 복구

무조건 timestamp를 덮어쓰는 복구는 금지한다. 대상 product/import/job/attempt, 두 정확 timestamp, 본문·facts·asset·AI lineage 해시, 원본 response 해시, 해당 completion 원인, 후속 변경 없음의 증거를 고정한 **1회 감사 가능한 데이터 수리**를 별도로 설계한다.

최소 쓰기 후보는 위 증명이 모두 참인 경우에만 product의 잘못 이동한 updated_at을 원래 승인 기준으로 수리하고, 승인 레코드·원래 job binding·본문·버전·status·stock 등 다른 필드는 그대로 보존하는 것이다. 이 후보는 현재 금지된 수동 강제복원의 대체를 자동으로 허용하는 것이 아니다. 총괄이 증거와 실제 트리거·ACL을 검토해 exact repair 경로를 구현해야 한다. 단순 UPDATE 실행 금지.

원본 무변경을 충분히 입증하지 못하면 이 후보는 적용하지 않는다. 승인 timestamp를 앞으로 이동시키거나 전역 stale 검사 제거로 우회하지 않는다. 모든 관련 read/source/asset/verify 가드가 정상 일치하게 되는지를 복구 후 읽기로 검증해야 한다.

### B. 상품 생성 거절 재조정

- exact job/attempt에 유일한 immutable reconciliation receipt를 둔다. 결론은 `product_create_rejected_no_product_found`, 부수 효과는 `image_upload_accepted`로 기록한다.
- 현재 동일 SKU 원격 0건, exact HTTP 400 오류, request/response hash, 판매 계정 결속, 후속 mutation 없음, 활성 경쟁 job 없음, 정상 종료·비실행 상태를 하나의 원자적 transaction 안에서 검증한다.
- 조건 만족 시에만 source job/attempt를 실패 terminal로 정리하는 전용 경로를 만든다. 원본 request/response/fingerprint/실행 시각/count/이미지 업로드 증거는 그대로 보존한다. `pre_gateway_retryable=true`로 거짓 분류하지 않는다.
- 오류 classifier를 전역적으로 느슨하게 만들지 않는다. 이미지 효과가 있는 다른 작업이나 timeout/5xx/네트워크 불명·일부 성공을 자동 재시도하지 않는다.

### C. 수정된 등록의 단 한 번 실행

- 원본 job 자체의 count/started/payload를 고쳐 재활용하지 않는다. 원본을 가리키는 successor 실행 또는 명시적인 재실행 계약 중 하나가 필요하다. 현재 구현에는 둘 다 없다.
- 권장 설계는 exact reconciliation receipt를 소비하는 successor permit 1개다. 새 request는 원본 대비 단위가격 경로만 허용된 차이가 나도록 검증한다: `unitPriceYn=true`, `totalCapacityValue=315`, `unitCapacity=10`, `indicationUnit=g`는 기존 기록에 나온 후보이며 상품 사실·현재 법적/채널 요구를 총괄이 재확인 후 확정한다. 판매가 3190과 승인 상세·SKU·shipping 등의 나머지 계약은 보존한다.
- successor job/attempt를 원본과 원자적으로 연결하고 unique source + 유효기간 + consumption count 1 + 동일 credential/account + release SHA + 승인 current 가드로 중복 전송을 막는다. 기존 exact 최초 claim 조건을 전역 완화하지 않는다.
- 기존 문서의 '새 create 금지'는 미해결 recon을 우회하는 재등록 금지다. 본 설계는 그 상태에서 실행할 수 없으며, 총괄이 정상 reconciliation/permit 계약을 먼저 완성해야 한다.
- retry가 다시 거절되거나 불명 상태면 그 source를 새로 보존한다. 자동 반복 등록이나 새로운 멱등키 회전은 하지 않는다. 성공하면 원격 ID·판매/심사 상태·가격·재고·상세와 8개 이미지 readback까지 마무리한다.

### 현재 DB와 대조하는 방법 — 읽기 전용

1. `BEGIN READ ONLY`와 UTC 세션에서 현재 `to_jsonb(p)`의 `updated_at` 값만 승인 당시 `timestamptz` 값의 `to_jsonb`로 치환한 **표현식**을 만든다. 행 UPDATE를 실행하지 않는다.
2. 해당 표현식에서 `external_detail_import_id`만 빼고 원본과 똑같은 PostgreSQL `jsonb::text → UTF8 → sha256` 산식으로 비교한다. JS canonical JSON 해시로 바꾸지 않는다.
3. completion이 status도 바꿨다면 원본 요청의 prior status 근거를 확인하고 status+updated_at만 치환한 표현식을 비교한다. 역사 상태가 직접 저장되지 않았다면 제한된 허용 상태 후보에 대한 읽기 전용 해시 대조로 유일한 일치를 확인할 수 있으나, 단순히 그럴듯한 상태를 가정해 쓰면 안 된다.
4. 일치하면 status/updated_at 이외 전체행 값이 승인 직후와 동일하다는 강한 증거가 된다. import ID는 별도 승인·job binding으로 검증한다. 이때 현재 원본에서 복원한 후보에 대해 `excluding updated_at` 해시도 새로 계산하고, 기존 commitment로 검증된 재구성값임을 표시한다.
5. 불일치하면 근거 없이 열을 계속 제외해 통과시키지 않는다. 새 스키마 열, 별도로 허용된 재고·reserved 변화, competitor timestamp 변화를 구분해 필요한 과거 값/audit를 찾는다. 검증되지 않은 내용이 남으면 timestamp 수리의 전체원본성 조건은 미충족이다.

### 전체행 commitment가 불일치할 때 확보·미확보 범위

확보: 정확 product/owner/SKU/AI/import/version/source 승인 시각, 승인 3언어 문서·8개 image/pixel digest 및 승인 원본. `detail-import-verified-server-row.json`은 같은 import의 승인 전 verified 단계 전체 payload/receipts다. payload와 receipts의 현행 동일성은 별도 해시 대조할 수 있지만 해당 파일을 이미 approved인 행으로 설명하면 안 된다.

미확보: 승인 payload는 product 전체행을 포함하지 않는다. `external_code`, `description`, `source_url`, `image_url`, `on_hand`, `reserved`, `reorder_point`, `cost_krw`, `demo`, `created_at`, `supplier_name`, `comparison_memo`, `competitor_query`, `competitor_monitor_enabled`, `competitor_checked_at`, `product_facts`, 일부 상세 메타 열의 **전체 값/과거값**을 문서·이미지 승인만으로 증명할 수 없다. 이름·facts 일부가 요청에 있어도 전체열 동일성과 동일하지 않다.

현재 결론: **실제 원본 전체행은 찾지 못했지만, 정확 전체행 hash commitment를 찾아 정상적인 read-only 검증 경로를 확보했다.** 총괄의 현재 DB 대조 결과를 받기 전에는 수리 가능하다고 단정하지 않는다. 실행 가능한 migration은 작성하지 않았다.

## 현재 DB 대조 결과 — 전체 원본성 미입증, 복구 보류

총괄이 실제 DB에서 과거 PostgreSQL 산식 그대로 검증한 결과를 전달받았다. 현재 상품의 `external_detail_import_id`를 제외하고 `updated_at`을 승인 시각으로 표현식상 복원한 뒤 status를 각각 비교했으나, 세 후보 모두 승인 직후 해시 `94947671...`와 불일치했다. 아래 값은 전달받은 **해시 접두부**이며 전체 해시를 임의로 보완하지 않았다.

| 표현식의 status | 실제 계산 해시 접두부 | 과거 `94947671...`와 일치 |
|---|---|---|
| active (현재 상태) | `c6f8e815...` | 아니오 |
| draft | `8a3dd535...` | 아니오 |

현재 `competitor_checked_at`에는 승인 뒤의 `2026-09-06T10:53:04Z` 갱신이 확인됐다. 따라서 completion의 `updated_at`/status만 복원하는 방식으로 상품 전체 원본성을 증명할 수 없다. 이 필드가 알려진 차이라는 사실은 나머지 필드가 모두 같다는 증명이 아니다. 과거 값이 없는 열을 임의로 제외하거나 현재 값으로 과거를 재구성해 통과시키지 않는다.

**최신 결론: 현재 증거로 exact timestamp repair와 successor migration을 보류한다.** 승인·원본 job·attempt·request·response·실행 횟수·시각·reconciliation 상태를 그대로 보존한다. 누락된 과거 필드값/audit를 확보해 전체 차이를 설명하거나, 변경 이유와 검토 범위를 명시한 정상 재검토 계약을 별도로 마련하기 전에는 승인 시각 수리나 등록 재시도를 열지 않는다. 실행 가능한 복구 migration 작성·운영 적용은 하지 않았다.
