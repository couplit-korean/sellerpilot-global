## 확정 결론

1. **현재 상품의 승인 상태가 깨져 자동 게시 작업대 자체가 열리지 않는다.** 상품 수정시각과 승인시각의 불일치가 공통 선행 장애다. 각 채널 인증·카테고리·정책 문제도 따로 있으므로 이 하나만 고쳐서 8채널 완료라고 하지 않는다.
2. **정상적인 일반 실행 경로 대신 특정 과거 job에 묶인 예외가 남아 있다.** 실행기 생존·스케줄 정상과 새 상품의 claim 가능 여부가 다르다.
3. **발견한 채널 필수값을 프로그램에 저장하지 않았다.** 쿠팡 카테고리와 고시/순중량 준비가 판매자센터 폼·문서에만 있고 자동 payload의 입력 원장에는 없다. eBay 정책 handoff도 없다.
4. **필수값 검사·입력 보존 수정은 개발/Preview에 있고 실제 운영에는 반영되지 않았다.** 전체 프로그램을 새로 만들 필요는 없지만, 현재 코드·DB·실행기를 끝까지 통합한 운영 검증이 미완료다.
5. **상품 생성, 결과 저장, 사후 조회, 복구가 하나의 정상 흐름으로 이어지지 않는다.** 네이버는 필수값 거절 후 이미지 업로드 때문에 recon, 11번가는 생성 후 결과 저장 실패로 recon이다. 화면은 이를 주로 외부 권한/수동 확인으로 보여 내부 결함을 가린다.
6. **Lazada와 Temu에는 별도의 외부 인증/승인 차단이 있다.** 이것을 나머지 6채널 자동화 미완성의 이유로 사용하지 않는다.

## P1-OBSERVABILITY: 완료 표시가 실패 원인을 가림

운영 등록 히스토리에서 이 상품은 채널4/완료1/권한3인데 progressbar=100이었다. [registrationActivityProgress](../app/_registration/registration-status.ts#L131)가 published+failed+blocked를 합산해 처리 종료율을 계산하고 화면은 이를 등록 진행률이라 부른다. 같은 파일의 blocked 라벨은 일괄 `외부 권한 대기`다. 내부 payload 누락·결과 저장 실패·승인 불일치를 외부 권한처럼 오해하게 한다.

gateway job `succeeded` 역시 API 상품 성공과 다르다. [gatewayJobCompletionStatus](../lib/channels/gateway-contract.ts#L534)는 확정 오류 응답을 정상적으로 수집한 경우 succeeded로 종료할 수 있다. 성공 판정은 response.ok + provider remote ID + 동일 SKU readback에 근거해야 한다.

수정 요구: 성공률과 처리 종료율을 분리하고, 단계별 첫 실패/해결 위치/자동 복구 가능 여부를 표시한다. 키 보관·읽기 통과·enqueue·provider 등록·readback을 별개 상태로 유지하되 사용자가 내부 DB를 열어야 원인을 알 수 있는 흐름을 없앤다.
