# 통합 상품 입력과 자동 등록 설계 — 2026-09-07

상태: 사용자 승인 후 공통/채널 입력 UI, 카테고리 typed metadata, 미완성 초안 서버 저장, 편집 context를 구현하고 신규 DB 두 개를 적용했다. 최신 완료·미완료는 [구현 원장](./통합상품등록-구현원장-20260907.md)을 따른다. 아래 전체 설계의 옵션 생성/증빙 첨부/전체 상품군 실증까지 완료했다는 뜻은 아니다. 기준 코드 `54d8265`의 기능과 [자동 업로드 장애 분석](./자동업로드-장애분석-20260907.md)을 확인했다. 기존 AUTO-01~08 안에서 수행하고 별도 중복 프로젝트를 만들지 않는다.

## 1. 사용자 흐름

**이미지 등록 → AI 초안 → 공통·상품군·채널별 정보 자동 채움 → 사람이 확인·보완 → 준비된 채널 자동 업로드 → 원격 결과 확인.**

1차는 SellerPilot에 상품 초안을 만들고 값을 자동 입력하는 단계다. 2차 검토 후 승인한 상품과 채널만 외부에 전송한다. 사람이 하는 보완은 SellerPilot 안에서 끝나야 한다.

- 이미지와 함께 기존 상품 자료·공급처 자료를 재사용한다. 저장된 판매자 설정도 불러온다.
- 이미지 분석 중에도 초안을 저장한다. 모르는 필수값 때문에 상품 초안 생성 자체가 막히면 안 된다.
- 목표 채널·판매 계정·국가를 정하고, 추천된 각 채널 말단 카테고리를 확인한다. 그 조합에 필요한 항목을 동적으로 만든다.
- 모든 등록 항목을 다룰 수 있게 만들되 처음에는 미입력·오류·확인 필요한 항목을 먼저 보여준다. 자동 입력된 값과 선택 항목도 펼쳐서 수정할 수 있어야 한다.
- 사용자가 승인한 준비 완료 채널을 병렬로 전송한다. 다른 채널의 인증·심사 대기가 준비된 채널을 막지 않는다.

## 2. 한 번 입력할 값과 별도로 둘 값

| 영역 | 대표 항목 | 저장·재사용 원칙 |
|---|---|---|
| 상품 공통 사실 | 상품명 원문, 브랜드, 제조사, 원산지, 실물 이미지, GTIN, 판매 구성 | 상품의 사실을 한 번 입력. 공통 사실 변경은 이 값을 참조하는 채널에 반영 |
| 상품군 공통 사실 | 식품의 성분·알레르기·순중량·보관법, 의류의 소재·치수, 전자제품의 모델·전원·인증 근거 | 상품군에 필요한 질문만 표시. 국가·채널별 고시 문구와 인증 요건은 별도로 변환·검증 |
| 옵션·묶음 구성 | 옵션 조합, 자식 SKU/GTIN, 옵션별 이미지·중량·재고, 박스 수와 내포장 수 | 상품 전체 공통값과 옵션별 값을 구분. 조합별 독립 행으로 저장 |
| 채널 판매 설정 | 현지 상품명, 채널 말단 카테고리/속성, 현지 가격·통화, 채널별 판매 수량·한도 | 공통 사실에서 자동 변환하되 채널·국가별 설정으로 저장. 환율·가격 정책은 근거와 시점 표시 |
| 판매자 계정 기본값 | 출고지, 반품지, 배송·결제·반품 정책, 물류지, 배송기간 | 계정·채널·국가·운영환경에 귀속. 확인된 기본값을 재사용하고 상품별 예외를 허용 |

이름이 같아도 의미가 다른 항목은 합치지 않는다. 배송 중량과 순중량, 주문 가능한 재고와 판매 구성 수량, 출고 국가와 원산지, 소비기한과 보관 가능 기간을 각각 보존한다. 제조사와 공급처도 가능한 한 별도 사실로 정규화한다.

현재 비스킷을 예로 들면 `1박스`, `박스 안 6봉`, `봉당 52.5g`, `박스 순중량 315g`은 서로 연결되지만 다른 사실이다. 쿠팡 수량 속성이나 스마트스토어 단위가격 값은 공식 항목의 의미·허용 단위를 확인해 변환한다. 배송용 포장 중량을 315g에서 추정하거나 내포장 6봉을 판매 박스 6개로 바꾸면 안 된다.

## 3. 입력 화면

화면 상단에 상품 이미지와 저장 상태를 두고, 아래를 세 영역으로 구성한다.

1. **공통 상품정보**: 모든 대상 채널에서 재사용할 사실과 구성. 적용 채널을 항목 옆에 표시한다.
2. **상품군 추가정보**: 추천 분류에 필요한 고시·성분·치수·옵션·인증 등. 공통 질문을 묶고 법역별 차이를 표시한다.
3. **채널별 추가정보**: 채널·국가 탭 또는 카드. 해당 채널에서만 필요한 항목, 계정 정책 선택, 현지 가격, 제한사항을 제공한다.

각 항목은 `자동 추출`, `기존 확인값`, `판매자 설정`, `사람 수정`, `확인 필요`, `충돌` 상태와 근거를 가진다. 낮은 신뢰도 숫자만 보여주는 대신 “뒷면 사진에서 소비기한을 읽을 수 없음”처럼 필요한 행동을 설명한다.

- 기본 보기: 필수 미입력·오류·검토 필요. 별도 보기: 자동 입력 전체, 선택 항목.
- 문자열, 숫자+단위, 예/아니요, 단일/복수 선택, 날짜, 반복 행, 이미지/증빙 첨부, 옵션 행렬을 지원한다.
- 쿠팡 고시 JSON을 사용자가 작성하게 하지 않고 제조사·원산지·성분 등 각각의 입력칸으로 만든다.
- 가격과 반품비 등 판매 조건은 저장된 승인 정책을 우선 사용한다. 계정에서 여러 정책이 조회되면 임의의 첫 번째 정책을 고르지 않는다.
- 초안 저장 실패를 명확히 표시한다. 새로고침·다른 기기에서도 서버에 저장된 값과 수정 출처를 복원한다.
- 상품 내용 조회/편집은 소유권을 확인한 초안 API로 가능해야 한다. 상세 승인 불일치가 검토 화면 전체의 GET을 막지 않게 하고, 실제 전송은 별도 승인 검증을 통과시킨다.

## 4. 하나의 항목 정의에서 화면·검증·전송을 연결

`채널 + 계정 + 환경 + 판매 국가 + 말단 카테고리 + 메타데이터 버전`을 기준으로 등록 요구사항을 만든다. 메타데이터를 공유 캐시할 수 있는 범위와 계정에 귀속되는 정책은 구분한다.

각 항목 정의에는 다음이 있어야 한다.

- 안정적인 항목 ID, 한글 표시명, 공통 사실 연결 키, 적용 범위.
- 값 타입, 단위, 허용 값/코드, 길이·범위·개수, 반복 항목 구조.
- 필수/선택 및 조건부 필수 규칙, 선행 항목과 의존 관계.
- 값 출처, 자동 채움 방법, 사람이 확인해야 하는 조건.
- 채널 요청 필드 연결, 생성/수정 가능 여부, 원격 조회 필드 연결.
- 공식 메타데이터·문서 근거와 확인 시점, 규칙 버전, 지원 여부.

공식 API가 제공하는 메타데이터에 문서 기반 보완 규칙을 결합한다. 화면만 지원하고 payload에서 버리는 항목, payload에는 필요한데 화면에 없는 항목을 허용하지 않는다. 미지원 타입/필수 매핑이 발견되면 `개발 지원 필요`로 식별해 사용자 미입력과 구분한다.

모든 선택 항목도 지원 목록에 포함하고 필요할 때 열어 입력한다. 현재 조건에 해당하지 않는 필드는 숨기되 왜 제외되는지 확인할 수 있게 한다. 카테고리 변경 시 보존할 공통 사실과 재검증할 속성을 나누고 더 이상 유효하지 않은 코드를 몰래 전송하지 않는다.

‘모든 채널 등록 조건 충족’의 범위는 **지원하는 채널·국가·카테고리의 공식 등록 항목과 조건을 빠짐없이 구현하고 검증했다는 뜻**이다. API 미제공 기능이나 심사·판매 권한까지 입력 화면이 해결한다고 약속하지 않는다. 전체 지원표에서 `지원`, `부분 지원`, `추가 구현 필요`, `외부 권한 대기`를 구분한다.

## 5. 자동 채움과 사람 수정 규칙

우선순위는 **명시적인 사람 수정 → 확인된 기존 상품 사실/계정 정책 → 근거가 있는 자동 변환·추출 → AI 후보**다. 서로 다른 근거가 충돌하면 값을 조용히 덮어쓰지 않고 함께 제시한다.

- AI는 이미지/OCR·공급처 자료로 후보를 만들고 출처를 연결한다. 카테고리 추천은 실제 말단 코드·속성 확인을 거친다.
- 순중량, 인증번호, GTIN, 소비기한, 실재고, 계정 정책 등을 이미지 외형만으로 만들어 넣지 않는다.
- 값 없음, 확인 필요, 실제 0, 실제 false, 해당 없음은 다르다. 예를 들어 미확인 배송비를 무료배송으로, 미확인 GTIN을 바코드 없음으로 처리하지 않는다.
- 해당 없음은 채널 규칙에서 허용될 때 이유/근거와 함께 저장한다. 일괄 `상품상세 참조`는 필수값 충족으로 세지 않는다.
- AI를 다시 실행해도 사람이 수정한 값은 유지한다. 대체 제안은 변경 전후를 보고 선택한다.
- 공통값을 바꿀 때 영향을 받는 채널을 표시한다. 채널별 재정의는 보존하되 사실 자체가 충돌하면 재검토 대상으로 만든다.
- 재고는 자동 업로드 간 무작정 복제하지 않는다. 실제 보유량과 채널별 판매 가능량을 기존 재고 원장/배분 규칙에 연결한다.

## 6. 저장·승인·실행 계약

논리 구조를 먼저 확정하고 기존 테이블/RPC를 재사용한다. 아래 이름은 설계 개념이며 신규 테이블 생성 지시가 아니다.

| 구조 | 보관 내용 |
|---|---|
| 상품 사실 초안 | 공통·상품군·옵션별 값, 근거, 작성자/출처, 확인 여부, 내용 버전 |
| 채널 요구사항 | 메타데이터 버전, 분류·속성·조건부 규칙, 항목과 요청/응답 필드 연결 |
| 채널별 초안 | 상품/판매자 계정/환경/국가/채널/카테고리, 공통값 참조, 재정의, 정책 선택, 저장 버전 |
| 승인된 전송본 | 승인한 상품 내용·상세 manifest·옵션·채널값·정책·요구사항 버전의 불변 스냅샷과 지문 |
| 실행 및 원격 계보 | 기존 job/attempt/listing을 사용한 create/update·원격 ID·요청 결과·재조회·재조정 상태 |

- 임시 초안은 미완성 값을 저장할 수 있다. 서버의 등록 검증은 최종 전송 시 엄격히 적용한다. 클라이언트 검증을 유일한 기준으로 삼지 않는다.
- 초안 PATCH는 기대 버전을 받아 충돌을 검출한다. 멀티에이전트/다중 탭의 같은 필드 쓰기를 조용히 덮어쓰지 않는다.
- 콘텐츠 버전은 실제 상품/상세/전송값 변화에 결속한다. 작업 상태나 최종 조회 시각 같은 운영 메타 변경으로 승인이 풀리지 않게 한다.
- 변경 영향에 따라 관련 승인만 무효화한다. 이미지·공통 사실 변경은 이를 사용한 전송본에 영향을 주고, 특정 채널 가격 변경은 해당 전송본을 다시 확인한다.
- 기존 승인 원본은 보존한다. 현재 `updated_at` 불일치 복구는 별도 검증된 마이그레이션/복구 계약으로 처리한다. timestamp를 되감아 승인된 척하지 않는다.
- 승인·검증·enqueue 사이의 변경은 같은 버전 계약으로 검출한다. worker는 가변 최신 초안을 다시 읽어 다른 내용으로 보내지 않는다.
- worker는 실행 직전 인증·대상 계정·요구사항의 유효성 등을 확인한다. 규칙 변경으로 요청 내용을 바꿔야 하면 재검토한다. 이미지 업로드 등 부수효과 전에 가능한 검증을 끝낸다.
- 생성 잠금은 상품/계정/채널/국가/환경의 기존 원격 계보에 걸고, 요청별 멱등키를 추가한다. 새 초안 버전이나 새 키를 만들었다고 기존 상품을 다시 create하지 않는다.
- 기존 원격 ID가 있으면 검증된 update 경로를 쓴다. 응답 유실/결과 불확실은 조회·재조정하고 자동 재생성하지 않는다.
- 원격 오류는 입력 필드로 연결한다. 예: `unitPriceYn` 오류를 해당 채널의 `단위가격 표시 여부` 입력 위치에 표시한다.

## 7. 준비 상태와 성공 표시

입력 준비와 실행 준비를 분리한다.

1. 입력 준비: 조건부 필수·고시·허용 값·단위·옵션·이미지·가격 검증.
2. 연결 준비: 실제 계정 인증/권한, 앱 활성 상태, 필요한 정책과 배송 계약.
3. 실행 준비: 승인본 일치, 지원되는 일반 worker 경로, 계보·중복 검사, 전송 전 검증.

세 가지를 모두 통과한 채널이 등록 가능하다. 화면에는 실제 산출된 `필수값 충족 수`, `사람 확인 필요 수`, `채널 연결 상태`, `자동 등록 상태`를 따로 표시한다. 채널 결과는 대기·전송·채널 접수·심사 중·등록 확인·판매 중·실패·재조회 필요를 구분한다.

HTTP 성공이나 job 종료를 판매 완료로 표시하지 않는다. 원격 ID와 동일 SKU/제목/가격/재고/이미지·상세를 채널별 조회 가능한 범위에서 확인하고, 조회 불가능한 항목은 그 한계를 남긴다. 실패를 성공률 분자에 넣지 않는다.

입력 화면 개선과 별도로 AUTO-01 승인 충돌, AUTO-02 실행 경로, AUTO-06 인증/앱 심사를 처리해야 한다. 앞선 운영 감사 시점의 Lazada/Temu 상태를 새로 확인하지 않은 채 오늘 해결됐다고 표시하지 않는다.

## 9. 기존 AUTO 작업과 병렬 소유권

아래는 다음 구현의 배정안이며 이번 문서 작성 중 구현 에이전트를 새로 실행했다는 뜻이 아니다. 실제 시작 시 원장에 담당·소유 파일을 먼저 기록한다.

- **AUTO-01 / 총괄**: 초안·승인 계약과 기존 상태 복구. DB/API 공통 계약 소유, 통합/운영 변경을 직렬 처리.
- **AUTO-02 / 실행 담당**: 일반 worker claim/송신 경로·릴리스 결속. UI/공통 초안 파일은 변경하지 않는다.
- **AUTO-03 / 입력 담당**: 통합 항목 정의와 저장 계약의 확정 후 공통·식품·쿠팡 입력 폼. 필요한 계약 변경은 총괄에 전달한다.
- **AUTO-04·05 / 채널 담당**: 채널별 공식 요구사항·매핑/재조회 지원 검토. 초기에는 별도 파일로 구현하고 공통 preflight/workbench 수정은 입력 담당 한 명이 통합한다.
- 계약이 확정되지 않은 동안에는 실행 담당의 독립 복구와 채널 담당의 메타데이터 검토를 먼저 진행한다. 의존 코드 세 개를 동시에 추측해 만들지 않는다.
- 현재 4슬롯은 총괄1+하위3. 이후 담당이 끝나면 같은 원장에서 다음 채널을 이어받는다. 공통 파일·동일 상품/계정 운영 쓰기의 동시 소유는 금지한다.

구현 순서는 **초안/승인·실행 경로 복구 + 통합 입력 기반 → 식품의 쿠팡 create 및 Smartstore 기존 상품 update → 다음 상품 재사용 검증 → 나머지 채널 확장**이다. 첫 1~2채널 검증을 모든 상품군 완성 뒤로 미루지 않는다. Lazada/Temu 외부 조건은 독립 진행한다.

## 10. 완료 판정

- 새 이미지 상품을 만들 때 확인되지 않은 값이 있어도 초안 저장·복원이 된다.
- 공통 사실 한 번의 보완으로 이를 참조하는 각 채널 값이 채워지고, 사람의 채널별 수정은 재분석·새로고침 후에도 유지된다.
- 같은 상품군의 다른 상품도 ID별 코드/SQL 예외 추가 없이 등록 준비가 된다.
- 카테고리·국가 변경, 옵션 추가, 단위 변경, 조건부 필수 발생, 실제 0/false, 다중 탭 충돌을 검증한다.
- 지원 범위 내 공식 필수 항목마다 화면·저장·payload 매핑·검증이 있으며 누락을 자동 검사한다. 선택 항목도 선언한 범위에서 입력·보존·전송된다.
- 승인 후 상태 기록만 변경하면 승인이 유지되고, 전송에 영향을 주는 내용 변경은 관련 승인 검증에 걸린다.
- 중복 클릭/타임아웃/worker 재시작에도 기존 create 계보가 중복 생성되지 않고, 기존 상품은 update로 처리한다.
- 1~2개 준비된 채널에서 **SellerPilot 입력 → 검토 → 자동 요청 → provider 응답 → 원격 재조회**를 확인한다. 수동 판매자센터 등록은 이 증거를 대신하지 않는다.

문서 설계 완료와 소프트웨어 구현 완료를 구분한다. 이번 문서만으로 개발 진행률이나 자동 업로드 성공률을 올리지 않는다.
