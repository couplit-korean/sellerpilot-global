## 우선순위와 10시간 작업 순서

1. **첫 2시간:** 배송값 유실·송장 필수값/재조회·AI 복구 결함을 병렬 수정하고 각 계약의 행위 테스트를 통과시킨다. 다른 분과가 교차 검토한다.
2. **다음 2시간:** 통합 타입검사·린트·배포 빌드·주요 DB 계약 재생을 검증한다. 현재 production 정의와 migration 이력 불일치를 따로 대조한다.
3. **다음 3시간:** 준비된 채널부터 실제 원본 기반 상세 revision을 생성·검수한다. 기존 상품은 원격 ID를 보존하고 배송·가격·이미지 차이를 검토한다. 필요한 계정·권한이 없으면 해당 채널을 대기 상태로 남긴다.
4. **남은 3시간:** 허용된 채널별 실제 제출·재조회, 실제 문의/주문이 있는 범위의 CS·배송 검증, 실패/정합성 이력과 운영 문서 정리를 진행한다. 외부 승인이 안 끝난 채널을 완료로 계산하지 않는다.

이는 당시 복구 시작 시점의 작업 순서와 목표 배분이다. 아래 최종 통합 검증까지 끝난 코드 수정을 새 Aside 작업에서 처음부터 반복하지 않는다. 남은 작업의 시간 배분은 Aside 인계 문서를 따른다. 생성 API 혼잡, 계정 사용 한도, 승인 대기, 실주문·문의 부재가 있으면 전체 완료 시점은 연장된다.

## 운영 DB와 재현성 문제

production ref `sqaoqucxakebqkiygdxb`의 migration history는 270개/`20260902112000`에서 끝나지만 최신 함수는 존재한다. 20:30 KST 읽기 확인에서 inventory receipt/reserve/confirm와 local recovery claim은 service_role 전용이며 anon/authenticated 실행이 차단되어 있었다. 상세 저장/문의 history RPC는 authenticated 실행 경로가 별도로 존재한다. 이 확인은 모든 DB 정의가 소스와 같다는 뜻은 아니다.

초기 clean-checkout 전체 TS 테스트는 1,943개 중 1개가 로컬에만 있는 Shopee 복구 SQL 의존성 때문에 실패했다. 해당 무관한 파일 의존성을 없애고 실제 배포된 Smartstore 읽기 migration이 gateway/credential 상태를 직접 바꾸지 않는지 검증하도록 정리했다. 기존 untracked SQL은 수정·커밋·적용하지 않는다.

초기 MJS/DB 검사는 794개 중 47개 실패했다. 이 중 렌더 테스트 1개는 필수 빌드 산출물 없이 실행한 검증 순서 문제다. 나머지는 오래된 순차 실행/worker 토큰/Studio 차단 UI 기대값, 역사적 fixture에 이후 migration이 섞이는 문제, 실제 fresh migration 계보 누락으로 분리한다. 특히 `20260904211500`은 소스에 없는 이전 live overlay preimage를 요구한다. 과거 guard를 느슨하게 하거나 무조건 재실행해 해결하지 않는다.

기존 Supabase 호환 테스트 계층에서는 282개 migration 뒤 283번째 `20260904211500`에서 실패를 재현했다. 이는 실제 Supabase CLI 신규 설치 성공 주장이 아니다. 엄격한 statement history를 적용하면 더 이전의 운영자 적용 이력 guard에서도 멈춘다. tracked scripts/docs, Git 전체 refs, stash 및 확인 가능한 로컬 산출물을 검색했지만 정확한 선행 overlay SQL을 찾지 못했다. `20260904232000`은 운영 함수의 후속 snapshot으로, 누락된 이전 정의를 대신하는 증거가 아니다.
