## 1. 판정과 이전 보고 정정

**이전의 권한 확보 + migration 3개 + 배포 + 48시간 관측만으로 전 채널 CS 완료를 판정할 수 없다. 로컬 구현 전체 완료라는 이전 표현도 철회한다.** 저장·조회 기반과 주요 수집 어댑터는 구현됐지만 실제 재처리 실행, 보관 정책, 범위별 정합성, 채팅 어댑터, 통합 검증에 개발이 남아 있다. 이 문서가 이전 완료 표현보다 우선한다.

33개 기존 작업을 버리지 않고 아래 A01~A15로 구체화한다. 원래 항목의 세부 작업이므로 48개 독립 기능이 완성됐다는 식으로 숫자를 합산하지 않는다. 각 항목은 구현 산출물과 수용 시험을 통과해야 닫는다. 외부 권한 대기는 해당 어댑터가 구현됐음을 뜻하지 않는다.

완료는 계정 × 국가/shop × 문의종류 × 보관범위 × 수신/답변/첨부 기능의 교집합으로 판단한다. 로그인, API 읽기, 0건 응답, DB 저장, 화면 표시, provider 접수, 원격 답변 관측은 별도 증거다. 보관기간 밖 자료와 API 미제공 기능이 남으면 그 범위를 공개하고 전체 자동연동 100%로 표시하지 않는다. 미래 영구 무장애를 보증하는 표현은 사용하지 않는다.

## 5. 구현 구조와 데이터 계약

공통 인증·HTTP·서명·rate limiter는 재사용한다. 상품 등록 builder나 배송 mutation에 CS 코드를 추가하지 않는다. 채널 adapter는 provider contract만 담당하고 저장·일정·UI는 공통 CS 계층이 담당한다. 동일 gateway를 사용해도 CS 현재조회/과거조회/답변/상품/배송의 claim scope와 예산을 구분한다.

흐름: `capability scope → read/webhook receipt → raw verification → normalized revision → ticket/conversation → reply request → provider receipt → remote observation`. 과거 스캔은 별도 `scan → page → outcome → reconciliation`을 갖고 receipt와 메시지 ID로 연결한다. raw 재처리는 원래 sender/event/source를 유지하고 고객 발송 경로를 호출하지 않는다.

| 제안 계약 | 필수 필드·규칙 |
|---|---|
| capability scope | channel, immutable account/shop/country/app binding, ticketKind, operation, supported/permission_pending/unverified/provider_unavailable, verifiedAt, evidenceRef, retention start/end |
| history scan | scanId, scope, fixed from/to 및 timezone, provider contract version, cursor, pages, observed unique IDs, completeAt, reconciledAt, missingRanges, exclusions |
| page outcome | raw row → normalized/duplicate/quarantined/excluded/unprocessed 중 정확히 한 결과. ticket 수와 message 수를 원격 행 수와 동일시하지 않음 |
| raw processing | receiptId, digest, original credential binding, sourceKind, parserVersion, status, attempt, lease, nextAttemptAt, failureCode, firstObservedAt, expiresAt |
| revision | provider message ID, revision ID 또는 content digest, role, occurredAt/unknown, observedAt, eventKind, recall target, source receipt. 관측 시간을 발송 시간으로 대신하지 않음 |
| reply observation | ticket/expectedLatestInbound, target shop/recipient/parent, request fingerprint, provider receipt, remote evidence/time, outcome. provider 접수만으로 remote_observed가 되지 않음 |
| attachment | 원본 metadata, digest/size/mime(실측 가능할 때), source URL/expiry, storage policy, private object reference 또는 unavailable reason |
| health | scope별 lastAttempt/lastSuccess/lastInbound, oldest pending, queueAge, permission/key expiry, rate-limit retry, raw capacity, archive gaps |

DB 객체 명칭은 제안이며 구현 전 기존 schema/RPC를 확인해 확정한다. private table과 최소권한 RPC를 유지하고 승인 관리자 공용 운영 공간 정책을 보존한다. admin 해제·로그아웃 후 이미 표시한 민감 데이터와 캐시도 제거해야 한다. GRANT와 RLS는 별도 검사한다. [Supabase 공식 API 보안](https://supabase.com/docs/guides/api/securing-your-api).

## 6. 과거 자료 복구·정합성 절차

1. 계정/shop/kind별 최초 제공일·보존기한·조회 가능한 상태/폴더를 확인해 범위 manifest를 고정한다. 지금 시각이 매 페이지 바뀌어 조회 구간이 이동하지 않도록 한다.
2. 현재 수신을 유지한 상태에서 과거 수집을 낮은 우선순위로 시작한다. 새 이벤트는 원문으로 먼저 받으며 bootstrap과 같은 ID/revision이면 중복만 제거한다.
3. 각 페이지 저장과 cursor 전진을 원자적으로 연결한다. 실패 시 마지막 저장 페이지 다음부터 재개한다. 공급자 총수 변화는 별도 재대조 pass로 처리한다.
4. `원격 고유 행 = 정상 처리 + 중복/기존 관측 + 격리 + 근거 있는 제외 + 미처리`를 동일 snapshot/범위에서 확인한다. 격리는 누락은 아니지만 의미 해석 완료도 아니다.
5. 원격 총수·ID가 없는 API는 공식 종료 계약과 날짜 분할 및 판매자센터 범위 대조를 근거로 남긴다. 0건 응답 하나를 과거 전량으로 판정하지 않는다.
6. 종료 후 gap map과 오래된 열린 문의를 다시 검사한다. 실제 웹에서 기간·계정·문의종류·본문·역할·첨부·수정·회수 표시를 대조한다.
7. 공식 보존기간 밖 자료는 export/기존 백업의 실제 존재를 확인한다. 파일이 없으면 복구 불가/미확인 기간으로 남기며 가상 원문을 만들지 않는다.

eBay GetMyMessages의 날짜·상세 조회 제한은 [공식 문서](https://developer.ebay.com/devzone/xml/Docs/Reference/ebay/GetMyMessages.html)를 따른다. 이전 UI21/API9는 분모가 같은지 원격 ID 대조가 더 필요하다. 단순 21−9로 특정 12개 행의 신원이나 Commerce로 복구 가능함을 확정하지 않는다.

## 8. 필수 수용 시험

- **원문/재처리:** 저장 실패 ACK 차단, ACK 뒤 프로세스 중단, parser upgrade, 중복 delivery, 다른 credential, 256KB와 5,000행 경계, 만료 임박 pending, quarantine 실패.
- **과거/페이지:** empty+hasMore, missing total, 반복 cursor, 마지막 페이지 누락, 101세션/101메시지, Shopee 여러 shop, 날짜/윤일/시간대, 7/35일 중단, 제공기간 밖.
- **역할/변경:** 판매자 외부 답변, 시각 없음, 역순, 동일ID 다른본문/첨부, 회수 대상 없음, unknown status, 새 고객 문의 도착 중 이전 답변 완료.
- **송신/관측:** provider ACK 유실, 429/5xx, timeout 후 remote 성공, 잘못된 shop/parent/recipient, 동시 클릭, 버튼 disabled 우회 API 호출, read만 수행한 이벤트. 중복 송신은 0.
- **웹/권한:** 실제 관리자 로그인→검색→다음 페이지→대화→첨부→새로고침, 360px 화면, 관리자 해제, 세션 만료, 권한 에러 때 이전 데이터 제거, HTML 미실행, URL 만료.
- **유지/격리:** 8shop+1년 eBay+신규 문의 동시 부하, backoff, token 갱신 CAS 실패, 상품·배송 동일 worker 경쟁, 읽기 전용 주문 연결, 백업 복원 후 tombstone 보존.

SLO는 초기 설계 목표로 Push 내부 저장→화면 p95 60초, 폴링은 계획 주기+실측 처리시간, 지연 경보는 scope별 정상 주기 2회 초과를 사용한다. 공급자 생성→API 노출 지연은 별도 측정한다. 성능 합격치는 실제 quota/부하 측정 뒤 확정하며 작업 제안 수와 drain capacity의 단순 산술로 합격하지 않는다.

## 9. 최종 보고 기준

채널별 `권한 확인 / 구현 / 로컬 검증 / 운영 적용 / 과거 대조 / 실제 답변 관측 / 복구 시험 / 관측 기간`을 각각 기록한다. 전체 기능 inventory가 확정되기 전 임의 개발률을 만들지 않는다. 이미 통과한 235 CS·39 DB·68 경계 검사는 이전 소스의 테스트 증거이며 이번 문서 검토에서 재실행하지 않았다. 전체 저장소/실운영 완료로 확대하지 않는다.

최종 통과는 필수 scope의 미수집·해석 미완료·미확정 답변·미검증 경계가 0이고, 제외/복구 불가가 명시되어 있으며 사용자가 요청한 전체 범위와 일치할 때만 선언한다. 지원 불가한 공급자 기능은 프로그램 100% 자동연동의 잔여 제한으로 남긴다.
