## 3. P0 실행 순서 — 총괄과 DB 검증 담당이 즉시 협업

### A. 현재 작업 실행 경로 확정

- 총괄은 기존 job의 상태/시간/attempt/원격 ID와 필요한 현재 승인·릴리스·토큰 메타데이터만 읽고 공유한다. 하위가 같은 운영 조회를 반복하지 않는다. 비밀값 원문을 공유하지 않는다.
- 20:56 기록의 서버리스 응답은 HTTP 200이지만 claimed=0, processed=0이었다. 21:04에는 claim 함수의 스마트스토어 제외 조건을 바꾸는 후보 SQL만 작성했다. 21:20에는 로컬 게이트웨이 claim 경로까지 조사했다. **현재 어느 워커가 어떤 조건으로 이 작업을 가져가야 하는지 먼저 확정한다.**
- 인계에 남은 internal_schedule_requests PK 충돌은 조사 가설이다. 최신 drain 응답·실제 함수·로컬 고정 IP 워커 조건과 대조하고 단독 확정 원인으로 취급하지 않는다.
- `20260906211000_allow_approved_smartstore_external_create_claim.sql`은 후보안이지 적용 완료가 아니다. 전체 스마트스토어 허용으로 넓히지 않는다. 의도된 고정 IP 경로, 승인 영수증, 요청 소유권, live intent, 작업 종류, 토큰 scope/version, 중복 claim 차단을 유지하는지 검증한다.
- DB 담당의 기존 PK 충돌 조사 결과부터 회수하고 새 증거와 대조한다. DB 담당이 정확한 함수와 전후 조건·양성/음성 회귀·적용 및 되돌림 절차를 제시하고 총괄이 검토한다. 운영 변경은 총괄 한 명만, 필요한 범위만 실행한다. 후보 SQL을 내용 확인 없이 적용하거나 마이그레이션을 일괄 재생하지 않는다.

### B. 기존 작업 처리와 원격 확인

- queued/running/결과 불명인 기존 작업에 새 create·새 멱등키·새 attempt를 추가하지 않는다. 새 recon 작업 생성·재조정 요청이나 수동 drain/강제 claim/락 제거/강제 실패처리로 우회하지 않는다. 기존 reconciliation 원본 보존과 결과 확인을 위한 읽기 전용 원격 조회는 유지한다. 올바른 실행 경로를 복구한 뒤 정상 소비를 확인한다.
- 이미 원격 ID가 생겼으면 바로 해당 상품을 재조회한다. timeout/HTTP 202/응답 유실은 완료도 실패도 아니다. 기존 요청과 SKU/상품의 원격 상태를 맞춰 확인한다.
- 기존 작업이 정말 종료됐고 원격 생성도 없다는 근거가 있는 경우에만, 정상 재시도 계약에 맞는 복구를 검토한다. 새 시도 필요 사유·이전 계보·중복 없음 증거를 원장에 먼저 남긴다.
- 완료 기준: 원격 상품 ID, 실제 상태(판매/심사/비공개), 가격·재고·배송 조건, 승인 상세·이미지, SellerPilot의 작업 결과 및 사용 화면 경로 일치. 심사중이면 등록 접수와 판매 가능을 나눠 보고한다.
- 첫 성공은 즉시 사용자에게 보고한다. 다른 8개 담당 완료를 기다리지 않는다. 같은 상품을 다시 등록해 화면 증명을 반복하지 않는다.

## 5. 재작업·누락 방지의 실제 운영 규칙

- 공용 원장은 총괄만 수정한다. 한 행에 task ID / 실제 담당 / 상태 / 기준 commit+변경 파일 해시 / 승인 버전 / 소유 파일·탭·외부 대상 / 현재 job·attempt / 완료 기준 / 증거 / 다음 행동 / 갱신 시각을 둔다. 예정 담당과 실제 RUNNING을 구분한다.
- 상태는 CHECK, TODO, RUNNING, READY, BLOCKED, DONE을 사용한다. READY는 통합/운영 검증 전이다. 하위 종료 알림은 DONE 근거가 아니다. 하위8종료를 전체8채널완료로 표시하지 않는다.
- 착수 전 같은 목표/파일/채널/상품/operation/승인 버전/요청 지문의 기존 행을 확인한다. 동일 작업은 기존 ID를 재개하고 새 ID로 숨기지 않는다. 총괄 P0-03와 CH-SS는 동일 외부 실행 1건이다.
- 변경 없는 동일 소스·입력·계약의 통과 결과는 재사용한다. 새 테스트가 필요한 경우 바뀐 코드/입력, 과거 테스트 공백, 최소 재검증 범위를 먼저 적는다. 새로 추가한 회귀는 필요한 범위에서 실행하되 검사 개수를 다른 실행과 중복 합산하지 않는다.
- 공유 파일·탭·원격 상품의 쓰기는 동시에 한 담당만 한다. 파일 소유권 이전 시 현재 담당이 쓰기를 멈추고 패치·기준 해시를 전달한 뒤 이전한다. 하위가 공통 문서, 전체 포맷, 일괄 commit/push를 하지 않는다.
- 전체 타입 검사/빌드는 같은 체크아웃에서 하나만 실행한다. 통합된 판본에 대해 필요한 검사를 한 번 수행하고 결과를 공유한다. 실제 코드 변경 시 해당 Next.js 버전의 로컬 가이드를 읽는다.
- 승인 이미지와 영수증, 이전 실패·reconciliation 원본, 기존 원격 ID, job/attempt 계보를 보존한다. 중복 방지를 위해 결과를 삭제하거나 상태를 강제로 완료 처리하지 않는다.
- 보호 파일 `supabase/migrations/20260903150000_unblock_shopee_second_oauth_deadlock.sql`은 읽기·수정·삭제·복사·스테이징·커밋·테스트 입력·운영 적용 모두 제외한다.
- 현재 사용자 브라우저 라우팅 지침을 따른다. 과거 문서의 프로필 예외를 최신 지시보다 우선하지 않는다. 사이트별 실제 판매자, Vercel 팀, Supabase 프로젝트는 확인하고 불필요한 로그아웃·키 교체·앱 연결 해제를 하지 않는다.
- 신규 고객 답변 발송, 실제 출고, 임의 주문·가격·재고 변경, 유료 구매, main 변경은 이번 실행 범위가 아니다. 꼭 필요한 사용자 입력은 기존 승인 기록부터 확인해 미해결 항목만 한 번 모아 요청하고 독립 작업은 계속한다.

## 6. 보고와 종료 기준

첫 보고는 실제 가동된 담당/슬롯, 스마트스토어 기존 job 상태, 바로 할 동작만 짧게 한다. 첫 성공 전 약 15분마다 채널·현재 단계·새 증거·차단 원인·다음 동작을 보고한다. 같은 외부 차단에서 새 근거 없이 반복하지 말고 다른 독립 작업을 진행한다. queued 스마트스토어를 방치하거나 지워서 다른 채널 성공으로 덮지 않는다.

첫 성공 즉시 채널/원격 ID/등록 내용/판매 또는 심사 상태/사용 화면 경로를 보고한다. 그 후 두 번째 채널과 나머지 병렬 성과를 이어서 통합한다. 8개 하위 전부 종료할 때까지 첫 성공 보고를 미루지 않는다.

마감 전 무담당 작업, 실행자 없는 RUNNING, 증거 없는 DONE, 겹치는 파일·탭·외부 쓰기, 누락된 사용자 입력, 원격에만 존재하는 수정, 로컬 미통합 변경을 대조한다. 차단된 항목도 담당·원인·다음 행동을 남긴다. 공용 원장·현재상태·운영 보고가 같은 최신 사실을 가리키도록 맞춘다.

진행률은 전체 추정 약70%(판단치)와 첫 등록0/1·새 상세8채널게시0/8(마지막 기록)을 분리한다. 내부 큐/HTTP202/테스트/배포만으로 등록률을 올리지 않는다. 외부 인증/심사는 종료 시간을 보장하지 않는다.
