## 1. 결론과 이전 보고 정정

원문 보존, 범위별 수집 증거, 답변 접수와 원격 관측 분리, 자격 결속, 재처리와 복구 상태를 공통 계층으로 유지했다. 이번 감사에서 재현했던 주문/자격 결속, import 상태·대용량 재개, 실제 요청 단위 예산의 로컬 코드 공백은 닫았다. 남은 항목은 실제 provider 권한과 공식 원본 형식, 운영 migration 적용, 과거 원격 ID 전량 대조, 승인된 시험 문의의 원격 답변 관측이다.

공용 gateway를 `serverless-cs-gateway`에서 `serverless-gateway`로 이동한 것은 명칭과 진입점 정리다. 전체 구현이 이동했고 기존 파일은 re-export한다. 공용 실행부와 `operations.ts`는 CS와 상품/주문 모듈을 함께 사용한다. 공통 인증·전송·dispatch를 공유하는 것은 설계상 허용되지만, 이 이동만으로 실행 자원까지 분리되었다고 말할 수 없다.

## 3. 이번 재검토에서 발견한 개발 공백

### P0-1: 주문·자격 변경 뒤 잘못된 문의 연결 유지 — 로컬 수정·회귀 통과

근거: `supabase/migrations/20260908001000_harden_cs_commerce_boundaries.sql:75`의 주문 trigger는 NEW 소유자·채널·주문번호에 일치하는 문의만 재검사한다. OLD 식별값에 연결된 문의를 방문하지 않는다. 자격증명 자체의 채널/소유자 변경을 반영하는 trigger도 이 migration에 없다.

기존 시험의 fixture에 이 migration을 실제 적용한 격리 PGlite에서 다음 세 경우를 각각 실행했다.

| 변경 | 실제 결과 | 기대 결과 |
|---|---|---|
| 주문 외부번호 변경 | still_linked=true, status=exact, actually_exact=false | 이전 연결 해제 후 unmatched 등 유효 상태로 갱신 |
| 주문 소유자 변경 | 동일 | 잘못된 소유자 연결 해제 |
| 자격증명 채널 변경 | 동일 | 연결 해제 후 unverified_credential |

운영 DB에서 발생했다고 확인한 것은 아니다. 로컬 migration은 OLD/NEW 영향 문의의 합집합을 재검사하고 주문 삭제·demo 전환·NULL credential·자격 변경/삭제를 반영하도록 수정했다. 주문 결속 DB 시험 12/12가 통과했다. 실제 PostgreSQL 다중 세션 lock 동작은 운영 전 preview DB에서 다시 검증한다.

### P0-2: 작업 예산과 실제 공급자 호출 수의 차이 — 로컬 수정·회귀 통과

job 최초 예약과 실제 provider HTTP 호출을 AsyncLocalStorage 실행 문맥으로 결속했다. 첫 요청은 job 예약을 소비하고 두 번째부터는 매 요청마다 RPC 예산을 예약한다. serverless와 Mac worker가 같은 전용 rate-budget 경로를 사용한다. 현재조회→답변→과거조회 claim 순서, 429 재대기, 불확실 답변 재송신 금지 회귀가 통과했다. 공급자별 실제 일/분 quota 수치는 운영 호출 헤더와 공식 계약으로 보정해야 한다.

### P1-1: 취소한 import의 응답 상태 오류 — 로컬 수정·회귀 통과

API와 화면이 DB의 `staging|preview_ready|committing|committed|cancelled` 상태를 그대로 검증한다. cancelled/committed 재시도는 terminal 상태를 보존하고, committing 재개는 완료되지 않은 행만 계속한다. 실제 행 미리보기는 `new_ticket|new_message|duplicate_message` 결과와 cursor를 반환한다.

### P1-2: import 크기·처리량 계약 미정렬 — 로컬 수정·회귀 통과

브라우저는 파일 총 32MB/10만 행을 검사하고, 원본 SHA-256에 결속된 60만 byte 이하·최대 500행 조각만 API에 보낸다. API는 1.25MB 초과 요청을 DB 전에 거절하고 각 행을 다시 정규화한다. DB stage는 batch source digest를 재검사하며 첫 누락 행을 반환한다. commit도 500행 transaction으로 분할돼 브라우저/서버 중단 뒤 재개된다. 공식 export가 없는 채널의 임의 parser는 계속 비활성이다.

### P1-3: 구조 경계 시험의 검증 범위 제한 — 로컬 수정·회귀 통과

직접 import 검사에 `@/` alias 해석과 re-export를 포함한 전체 app/lib import graph 탐색을 추가했다. CS와 상품 등록 양방향에서 간접 의존도 검사하며, 명시한 공용 gateway/operations/protocols 경계만 탐색 중단점으로 허용한다. 정적 경계 3/3과 CS가 상품·배송 mutation을 만들지 않는 DB negative test가 통과했다. 공용 worker를 물리적으로 분리한 것은 아니며 operation·credential·lane 예산과 mutation fence로 격리한다.

### P1-4: Shopee 반품/환불 이력 공백 — 로컬 수정·회귀 통과

공식 Returns 목록은 생성·수정 기간 조회가 최대 15일이고 페이지당 최대 100건이며, 상세 증거는 return serial별 별도 API에서 제공된다. 상품 후기 adapter와 ID를 섞지 않고 `shopee:return:{shopId}:{returnSn}` 티켓으로 정규화했다. 목록 큐를 job당 상세 10건으로 제한해 timeout을 피하고, 같은 shop의 큐·다음 페이지를 모두 끝낸 뒤 다음 OAuth shop으로 이동한다. 반품 건은 `after_sales`, `replySupported=false`로 저장해 후기 답변 endpoint로 잘못 보내지 못한다. 격리 DB wrapper는 shop·return serial·remote message hash·읽기 전용 context가 정확히 일치할 때만 수용한다. 실제 8개 운영 shop 응답과 원격 총량 대조는 배포 후 읽기 전용 canary가 필요하다.

### P1-5: 쿠팡 취소·반품·교환 이력 공백 — 로컬 수정·회귀 통과

쿠팡 반품·취소 목록은 공식 v6 `returnRequests`의 `timeFrame`과 `RETURN|CANCEL`을 서로 다른 kind로 고정했다. 해당 조회에는 문서가 허용하지 않는 pagination·상태·주문 필터가 들어가면 실행 전에 거절한다. 교환은 공식 v4 `exchangeRequests`를 7일 미만 창, 페이지당 10건, 정확한 `nextToken` continuation으로 구현했다. 수집 결과는 `after_sales` 읽기 전용 티켓이며 주문번호·사유·상태·품목·송장 맥락만 allowlist로 DB에 저장한다. 전화번호·주소·빈 reply context가 아닌 입력과 클레임 mutation은 거절한다. 기존 25개 쿠팡 과거 작업은 동일 request key를 유지하면서 40개로 보충돼 중복 없이 재개된다. 실제 운영 credential 권한과 WING 원격 ID 전량 대조는 미실행이다.

### P1-6: Qoo10 취소·반품·교환 이력 공백 — 로컬 수정·회귀 통과

공식 `ShippingBasic.GetClaimInfo_V3`의 요청일·클레임 상태 계약을 일반 `CSCenter.GetInquiryMessage`와 분리했다. 현재 6일과 매일 최근 30일 작업은 별도 중복 키를 사용하고, 입력은 8/14자리 일본 시각·최대 90일·공식 상태와 검색조건만 허용한다. 결과는 최상위 배열과 `ResultObject.ClaimInfo`를 모두 처리하며 요청일·주문번호로 티켓 계보를 만들고 상태 수정은 revision으로 보존한다. 주소·우편번호·수취인·전화번호·구매자 식별자는 정규화 대상에 넣지 않고 DB allowlist가 다시 거절한다. 클레임은 읽기 전용이므로 일반 문의 답변이나 환불·승인 mutation으로 전달되지 않는다. 운영 credential 호출과 QSM의 기간별 건수·주문번호 전량 대조는 미실행이다.

### P1-7: 11번가 상품 Q&A 수신·이력·답변 공백 — 로컬 수정·회귀 통과

올바른 Seller Office 계정과 인증된 공식 상세 가이드에서 목록의 날짜·상태 입력, 응답 필드, 답변 XML과 성공 응답 결속을 확인했다. 전용 adapter·정규화·DB allowlist·30일 5구간 이력·관리자 화면·서버리스 허용표를 연결했다. 운영에서 이미 사용하는 `credential_incarnation_v1`과 향후 `provider_certified_v1` 계보를 11번가에 한해 허용하고, 미검증 legacy credential은 거절한다. DB 답변 작업은 최신 고객 inbound와 `brdInfoNo`·`prdNo`가 일치해야 생성되며 mutation fence 뒤 한 번만 전송한다. 상품 등록·주문·배송 테이블과 operation을 참조하지 않는 정적·동적 경계 시험이 통과했다. 운영 Key 원격 Q&A 조회, 과거 총량 대조, 실제 답변 echo는 미배포 상태라 아직 실행하지 않았다.

외부 앱 심사나 API 미제공 기능은 코드 완성으로 바뀌지 않는다. 공식적으로 제공되지 않으면 수동 연결·공식 export 등 지원 가능한 운영 절차를 표시하고, 자동연동 미지원으로 남긴다. 고객에게 실제 답변을 보내는 검증은 지정된 테스트 문의와 답변 내용이 승인된 경우에만 실행한다.
