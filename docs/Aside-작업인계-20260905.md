## 3. 모델과 멀티 에이전트

- 사용자는 기존 Codex와 같은 모델을 원한다. Aside `Settings → Models`에서 연결된 ChatGPT 공급자와 실제 선택 가능한 모델을 확인한다. GPT-6 동일 모델이 있으면 선택하고, 없으면 다른 모델을 같은 모델이라고 보고하지 않는다.

- 기본 하위 작업은 부모 모델을 상속하지만 일부 탐색 역할은 빠른 모델 범주를 사용할 수 있다. 같은 모델을 모든 작업에 쓰려면 각 작업의 실제 모델을 확인한다.
- 동시 슬롯 수가 작업 속도 배수나 10시간 완료 보장은 아니다. 하위 작업은 구체적인 작은 단위로 배정·회수하고 결과가 나면 다음 작업을 배정한다.

## 8. 시작 직후 실행 순서

1. Aside 작업 폴더를 위 로컬 경로로 지정하고 이 문서, `AGENTS.md`, `docs/현재상태.md` 상단 최신 상태, `docs/운영복구-20260905.md`, `docs/계정연결.md` 순으로 읽는다.
2. 아래 읽기 명령으로 실제 경로·브랜치·HEAD·변경 파일을 확인한다. 사용자의 기존 변경은 보존한다. 의존성 설치·전체 테스트부터 무조건 다시 시작하지 않는다.
3. Aside 기존 탭에서 SellerPilot, 대상 판매자센터, Vercel 팀, Supabase ref를 확인한다. 로그인 유무·계정 제한·API 권한은 각각 기록한다.
4. 총괄과 하위 최대 5개를 배정하고 파일·상품·주문 쓰기 소유권을 정한다. 모델·실행 한도가 다르면 실제 값을 첫 진행 보고에 적는다.
5. 총괄은 DB/release 선행 문제, 나머지는 독립적인 읽기 확인·소재/초안 검수·채널 권한·재고/주문 연결 분석을 동시에 진행한다.
6. 각 외부 변경 전 동일 SKU/상품/주문·기존 job·attempt·receipt·remote ID를 복원하고 재조회한다. 불명확한 이전 결과는 새 create/송신으로 덮지 않는다.

cd /Users/kimchangheemac/dev/sellerpilot
pwd -P

git rev-parse --show-toplevel HEAD
git log -5 --oneline
git ls-remote origin refs/heads/integration-aside

Aside 실행 셸에서 `node` 또는 `npm`이 없으면 새로 설치하기 전에 기존 런타임을 사용한다. 인계 때 아래 Node 실행 파일의 `v22.23.2` 응답과 npm 링크를 확인했다. 이는 현재 셸에만 PATH를 추가하며 전역 셸 설정을 고치지 않는다.

```bash

node --version
npm --version
```

Next.js 관련 코드를 쓸 때는 `node_modules/next/dist/docs/`의 해당 가이드를 먼저 읽는다. 검증은 바뀐 동작의 집중 테스트부터 하고 통합 시 필요한 전체 검사를 실행한다. 현재 package scripts에는 `npm run test:channels`, `npm run test:db`, `npm run lint`, `npm run build:vercel`이 있다. `npm test`는 vinext 빌드 후 MJS와 TS 순서다. 문서에 남은 15개 실패와 새 회귀를 구분하고 빌드 산출물이 필요한 렌더 검사는 빌드 후 실행한다.

## 9. 남은 작업의 10시간 배분

이 시간표는 Aside에서 새로 시작하는 잔여 작업 기준이다. 앞선 코드 복구에 이미 쓴 시간을 되풀이하는 계획이 아니다.

| 경과 | 총괄의 우선 작업 | 다른 담당이 병렬로 진행할 작업 |
|---|---|---|
| 0–30분 | 로컬·계정·모델·DB ref·운영 SHA 재확인, 작업 분배 | 8채널 상태·기존 상품·소재·실문의/주문 유무 확인 |
| 30분–3시간 | DB 누락 정의·이력 복구 방안 검증, 15개 실패 분류·해결 | 상세 제작 준비·실제 생성 가능한 경로 확인, CS/재고/배송 잔여 결함 수정 |
| 3–5시간 | 필요한 통합 검사, candidate·release·DB 정합성 검증 및 운영 전환 판단 | 새 이미지·상세 검수, 채널별 native payload·권한·정책 확정 |
| 5–8시간 | 준비된 release와 게이트 범위 안에서 실행 통합 | 승인된 상품 등록·수정 및 재조회, 가능한 CS·재고·배송 검증 |
| 8–10시간 | 남은 오류 재현·재조회, 완료 증거 대조, 문서·코드 저장 | 공개 화면·manifest·답변·송장·재고 일치 확인, 다음 작업 정리 |

DB 선행 문제로 배포가 막혀도 다른 담당의 검수·로컬 수정·계정 상태 확인은 계속한다. 외부 심사·권한·실문의/주문 부재는 정확한 대기 이유와 다음 행동을 남긴다. 시간 경과만으로 승인 또는 완료로 간주하지 않는다.

## 10. 영역별 완료 기준

| 영역 | 완료라고 보고할 증거 |
|---|---|
| 상세·이미지 | 실제 새 파일·revision, 원본과 제품 정체성/구성/규격 일치, 식품 사실·언어·글자·레이아웃 시각 검수, 승인본=업로드 manifest, degraded fallback 없음 |
| CS | 지원 문의 유형·권한 확인, 문의 ID 수집·중복 방지·전체 대화 보존, 승인된 대상/내용의 답변 1회 전송, 같은 답변 원격 확인 |
| 업로드 | 같은 판매자·SKU·카테고리·가격·재고·배송·이미지로 성공 확인, remote ID 결속, 원격 읽기 대조, 요청한 공개 상태·구매 화면 확인 |
| 상품·재고 | 명시한 변경 필드만 반영, 기준 재고 하나 확정, SKU/주문라인 결속, 예약·출고·취소·반품 중복 처리 방지, 외부 재고 일치 |
| 배송 | 실제 출고 대상 주문·품목·수량, 정확한 운송사·송장 1회 처리, 동일 송장 원격 조회, 배송상태 갱신, 취소·부분발송·불명확 응답 구분 |

실제 고객 메시지는 승인된 대상·내용에만 전송한다. 승인이 없는 경우 구체적인 초안과 검증 결과까지 준비한다. 실문의가 없으면 수신·답변 운영 실증 대기, 실출고 주문이 없으면 배송 운영 실증 대기라고 적는다. 취소 주문을 출고 테스트로 바꾸거나 가짜 주문·송장·상품 사실을 만들지 않는다.

## 11. 진행 보고와 마무리

첫 보고는 확인한 경로/HEAD, 현재 계정·모델·동시 작업 수, 총괄+담당 배정, 갱신된 운영 상태, 첫 실행 항목을 짧게 적는다. 이후 의미 있는 완료·실패·외부 대기·사용자 행동 필요 시 보고하고 독립 작업을 계속한다.

작업별 증거에는 확인 시각, 코드/release, 채널, 상품·주문 ID, job/attempt/receipt, 외부 결과, 원격 재조회, 공개 확인, 남은 문제를 남긴다. 고객 개인정보와 비밀 값은 마스킹한다. 다음 표를 마지막 보고에 사용한다.

| 영역/채널 | 코드·테스트 | 운영 반영 | 외부 실행·재조회 | 완료/대기 | 남은 문제·다음 행동 |
|---|---|---|---|---|---|
| 각 담당이 실제 확인한 항목 | 증거 | SHA/적용 증거 | ID와 결과 | 구분 | 구체적으로 기록 |

끝나면 `docs/현재상태.md`의 맨 위에 새 운영 확인 시각·증거를 갱신하고 이 인계의 오래된 항목을 정리한다. 필요한 코드·문서만 선택적으로 커밋하고 `git push origin integration-aside` 후 원격 SHA를 확인한다. 기존 미추적 SQL을 포함하지 않는다. force push하지 않는다. production 전환은 별도 release 검증 결과로 보고한다.
