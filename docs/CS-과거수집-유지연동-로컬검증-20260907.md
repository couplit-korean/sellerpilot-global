## 이번 미커밋 코드 수정

1. 쿠팡 상품 문의 `ALL`, 고객센터 `NONE` 및 `TRANSFER` 조회. 스마트스토어는 `answered=false`를 제거하여 판매자센터에서 먼저 답변한 문의도 다음 정기 조회에 포함한다. 조회 시간 범위는 그대로이며 기간 밖 기록까지 해결했다고 표시하지 않는다.
2. 쿠팡/스마트스토어가 `totalPages`로 다음 페이지를 명시하면 적은 건수의 페이지에서도 이어서 조회한다. 다음 페이지가 남았는데 빈 페이지가 온 경우 오류로 처리한다. 배열 자체가 없는 응답을 0건 완료로 계산하지 않는다.
3. 쿠팡·스마트스토어·Qoo10·Shopee 상품 후기·eBay ASQ·Temu 정규화가 잘못된 배열/행, 필수 문의 ID·본문 누락을 조용히 버리지 않고 실패를 반환한다. 실패 페이지가 섞인 결과, 다른 채널/작업 결과, 알 수 없는 단계도 성공 원장으로 넘기지 않는다.
4. 쿠팡/스마트스토어 답변 배열의 잘못된 요소와 동일 메시지 ID에 서로 다른 원문이 반환되는 충돌을 드러낸다. 충돌은 자동 덮어쓰지 않는다. **오류를 가시화한 것이 원문 보존 완료는 아니다.** 원문 격리와 부분 수집 재개는 후속 구현 대상이다.
5. 상품 등록/주문/배송 실행기는 수정하지 않았다. 채널 카탈로그의 Shopee CS 설명과 `sync-arguments.ts`의 CS 요청만 바꿨다. 공용 주문 timestamp normalizer는 건드리지 않았다. Shopee 답변 job에는 CS의 `shopId`·`itemId`·`commentId`·본문만 다시 구성해 넣으므로 요청에 섞인 상품등록 필드는 DB에서 제거된다.
6. 서버리스 CS 경로가 매일 03:00~03:04 KST에 읽기 전용 복구한다. 스마트스토어는 최근 30일 전체 2개 종류, 쿠팡은 최근 30일의 7일 구간 중 하루 1구간 5개 상태를 순환 재검사하고, Qoo10은 S1/S2/S3 최근 30일, eBay는 ASQ 최근 30일을 매일 재검사한다. Shopee는 5분마다 저장된 OAuth 대상 8개 shop을 각각 정확한 토큰으로 조회한다. 현재 조회와 이력 복구는 서로 다른 중복 키와 5분/60분 cooldown을 사용하며, 최악 5분 작업 상한 35건은 drain 용량 40건보다 작다.
7. 웹의 채널 검증 카드가 과거 제공 범위와 마지막 성공 시각을 함께 표시한다. 폴링 채널은 성공 후 15분이 지나면 `수집 지연`, 시각이 없으면 `시각 확인 필요`로 바뀐다. Lazada는 이력 조회 성공만으로 Push 수신까지 통과했다고 표시하지 않는다.
8. Shopee 수집 응답의 cursor·`more`·페이지 크기·댓글 필드를 엄격히 검사한다. 다음 페이지가 남았는데 cursor가 없거나 반복되면 실패하고, 로컬 호출 상한 뒤에도 `more=true`이면 완료로 저장하지 않는다. 답변 comment ID는 JavaScript 안전 정수 범위를 넘으면 DB enqueue와 공급자 호출 전에 모두 거절한다.
9. 공용 페이지 검증 모듈을 native Node 동적 원장 테스트에서도 같은 파일로 읽도록 `.ts` import를 명시하고, `noEmit` TypeScript 설정에서 `allowImportingTsExtensions`를 활성화했다. 번들 코드와 PGlite 원장 테스트가 서로 다른 모듈을 실행하지 않는다.

## 100% 판정 전 반드시 남은 구현/검증

1. **범위를 먼저 고정:** 판매 계정·마켓·문의 종류(상품 Q&A/구매자 대화/플랫폼 안내/반품환불)·조회 가능한 최초일·보관 정책을 각 채널별로 기록한다. API가 제공하지 않는 과거 답변은 제공 불가로 표시하고 공식 내보내기가 있으면 출처를 보존해 별도 가져온다.
2. **영구 진행 위치:** 채널/계정/문의종류/기간마다 최초·마지막 페이지와 완료 시각을 DB에 저장하고 마지막 페이지 저장 후에만 전체 완료로 표시한다. 현재 6일/14일 이동 조회만으로 장기간 중단 후 누락을 복구할 수 없다.
3. **오래된 문의 갱신:** 수정 시각 조회가 있는 API는 겹침 구간을 두고 증분 조회한다. 생성일 조회만 있는 API는 미해결 티켓 재조회와 허용 과거 기간의 분할 재검사를 병행한다. 보관 제한 밖의 복구 불가 범위를 숨기지 않는다.
4. **원문 우선 저장:** Push 수신은 서명·계정 검증 후 원문을 영구 저장한 다음 성공 응답한다. 첨부·알 수 없는 형식·수정·회수도 먼저 보존하고 재처리한다. 파서 실패를 빈 성공으로 처리하지 않되 실패 반복만으로 수집 완료를 주장하지 않는다.
5. **실제 수량 대조:** 같은 계정/기간/상태/종류로 판매자센터 원본 수와 수집 원장을 비교한다. 중복·누락 메시지 ID, 최신 시각, 페이지 수까지 대조한다. 0건 채널은 해당 조건의 0건 일치로만 기록한다.
6. **지속성 검증:** 토큰 만료, 429/5xx, IP 차단, 7일 초과 중단, 중복 Push, 순서 역전, 중간 페이지 재시작, 판매자센터 선답변을 검증한다. 마지막 성공 시각/지연/누락 구간을 웹에 노출하고 조치가 필요한 상태를 구분한다.
7. **웹 최종 대조:** 승인 관리자 접근, 과거 검색/페이지, 대화 역할·원문·첨부·회수 상태를 실제 기록과 확인한다. 고객 답변 왕복은 별도 명시적 발송 승인 후 검증한다.
