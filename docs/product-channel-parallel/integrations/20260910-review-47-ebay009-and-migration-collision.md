The original database fixture manually rewrote the job, attempt and listing to their pre-claim states before testing retry. A real worker crash leaves `running` / `running` / `queued`, and the generic lease reaper can leave `reconciliation_required` / `running` / `queued`. Both real states are now claimable only for the same bound job, attempt, listing, credential, SKU, offer, marketplace and request fingerprint. The recovery claim count is capped at two. If the second recovery lease also expires, one transaction returns the job to `reconciliation_required`, the attempt to `manual_required`, and the listing to `failed/external_action`; it cannot remain permanently `running` / `queued`.

The first worker integration also attempted the new RPC before the ordinary claim on every loop. During a rolling deployment, an older database could answer 400/404/501/503 and block every ordinary channel job. The split gateway worker now falls through to the existing ordinary claim only for an empty recovery queue or those compatibility-unavailable statuses. It remains fail closed for invalid-lineage 409, authentication, rate-limit and other provider errors.

The new spawned `--once` compatibility test then exposed a separate startup hang in the worker's local-release attestation: three synchronous Git metadata reads had no timeout, so a slow or contended worktree could block the gateway before its first claim. Each read now has a two-second hard timeout and `SIGKILL` fallback. The same test completes the recovery-400 to ordinary-204 path and exits in about 2.4 seconds instead of timing out after 30 seconds. The final integrated worker SHA-256 is `b1c3160611147837ca011a90d3009edb23d8323a22dc7a7fccfdcfddfc3c05e2`.
