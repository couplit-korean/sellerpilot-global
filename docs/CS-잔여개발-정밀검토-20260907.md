현재 상태는 **여러 채널의 기본 조회·답변, 내부 원장, 과거 검색/대화 화면이 구현되었지만 전 채널의 전체 이력과 지속 수집을 보장하는 공통 구조 및 일부 채널 기능이 미완성인 단계**다. “로컬 구현은 전부 끝났고 외부 연결만 남았다”는 판단은 현재 코드와 맞지 않는다.

## 5. 앞으로의 공통 구조

### 5.1 영구 진행 위치와 정확한 완료 조건

기존 gateway job/한국 이력 작업 원장을 확장한다. 아래 이름은 제안이며, 동일 역할의 기존 테이블/열을 먼저 찾아 중복 원장을 만들지 않는다.

| 논리 객체 | 핵심 필드 | 불변 조건 |
|---|---|---|
| 범위/권한 원장 | channel, sellerAccountKey, shop/country, inquiryKind, read/reply/push/history capability, retention, source, checkedAt | 자격증명 버전이 바뀌어도 같은 판매자 데이터의 소유 범위는 변하지 않음 |
| 수집 실행 | runId, 범위, 고정 from/to, mode=current/history/repair, asOf, status, expectedCount(nullable) | 실행 시작 때 범위를 고정. expectedCount 미확인을 0으로 저장하지 않음 |
| 수집 페이지 | runId, stream/session, cursorIn, cursorOut, payloadHash, readCount, persistedCount, quarantinedCount, nextDueAt | 원문/정규화 저장과 다음 페이지 예약이 원자적. 저장 실패 시 cursor 전진 금지 |
| 기간 커버리지 | account/kind, from/to, scanCompletedAt, reconciledAt, missingRanges, evidence | API 완료와 원격 대조 완료를 별도 상태로 관리 |
| 원문 수신함 | deliveryId, nativeMessageId, identity, observedAt, payloadRef/hash, parserVersion, parseStatus, attempt/error | 서명/대상 계정 검증 후 durable 저장 성공에만 webhook ACK |
| 메시지 revision/첨부 | nativeId, revisionId/hash, kind, role, occurredAt(nullable), observedAt, attachmentRef, revoke state | 수집시각을 발송시각으로 대체하지 않음. 수정과 불명 충돌 분리 |
| 답변 관측 | deliveryId, expectedLatestInbound, request fingerprint, providerReceipt, remoteObservedAt, comparison | provider ACK와 동일 문의/본문 원격 관측을 구분 |

한 API 행이 고객 문의+여러 답변으로 확장되므로 `원격 행 수 = 저장 메시지 수`로 비교하지 않는다. 페이지별 원격 행은 처리완료/중복/격리/정당한 제외/미처리로 정확히 분해하고, 별도로 생성된 메시지·revision 수를 기록한다. 조회 가능한 미처리 건이 남으면 전체 완료가 아니다.

### 5.2 수집과 복구

- 현재 수집은 last successful checkpoint부터 겹침 구간을 두고 조회한다. 공급자가 수정일 필터를 제공하면 활용하고, 생성일만 제공하면 미해결 티켓 재조회와 고정 과거 구간 검사를 병행한다.
- 매일 특정 5분 구간에 호출되었는지를 완료 기준으로 삼지 않는다. `next_due_at`이 지난 미완료 작업을 다음 실행에서 되찾는다.
- 50 continuation/실행 시간/행 수/바이트 상한은 안전장치로 유지하되, 상한 도달 시 잔여 위치를 보존하여 다음 실행에서 이어 간다. 무한 재시도 및 무제한 단일 응답을 허용하지 않는다.
- shop별/유형별 진행 상태를 따로 저장한다. 전체 8shop 중 7개 완료/1개 실패를 정확히 표현한다.
- 토큰 갱신은 credential 단위 잠금과 기존 CAS/원자 저장 계약을 유지한다. 저장 확인 전 새 토큰만 메모리에서 사용하는 상태를 완료로 간주하지 않는다.
- 긴 장애가 원격 보관 기간을 넘으면 복구 불가 구간을 명시하고, 공식 export/기존 백업으로 복구 가능한지 확인한다.

### 5.3 원문·삭제·권한

알 수 없는 형식도 허용된 공급자/계정의 이벤트이면 안전한 원문 저장과 재처리 대상으로 보존한다. 서명 불일치/다른 계정 payload는 정상 고객 원장에 넣지 않는다. 이미지/파일의 원격 URL만 보존할지 허용된 보관본을 만들지는 공급자 약관·접근권한·만료 규칙을 확인한 뒤 정한다. 비공개 저장, 관리자 권한, 링크 만료·잘못된 URL 처리를 갖춘다.

기존 승인 관리자 공용 CS 조회 계약을 유지하고, 키의 최초 등록자에게만 제한하는 회귀를 만들지 않는다. 원격 계정 결속과 관리자 열람 권한은 서로 다르다. 삭제 tombstone을 유지해 수집 재개로 삭제 자료가 되살아나지 않도록 한다. 업무 보관 기간은 임의로 영구/무제한으로 정하지 않는다.

Supabase 구현 시 기존 private schema와 RPC 경계를 유지한다. 신규 객체의 GRANT/REVOKE와 RLS를 별도로 검사한다. 최신 문서에서도 API 접근 권한과 행 정책을 다른 계층으로 설명한다. [Supabase API 보안](https://supabase.com/docs/guides/api/securing-your-api), [신규 테이블 기본 노출 변경](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically). 이번 검토는 운영 권한을 변경하지 않았다.

### 5.4 상품 등록·배송과의 관계

CS 어댑터 분리는 이미 진행됐으므로 거대한 재작성으로 되돌리지 않는다. CS가 공유해도 되는 것은 자격증명 저장/갱신·서명·HTTP·gateway 기반이다. 상품 게시·재고 변경·운송장 변경 operation과 업무 상태는 별도로 유지한다.

추가할 경계는 ①CS 전용 요청 스키마 ②operation별 잠금 키 ③CS/상품/배송별 재시도 예산 ④채널별 API 한도를 존중한 처리량 할당 ⑤중요 신규 문의가 오래된 이력 작업 뒤에서 굶지 않는 우선순위다. `35개 작업 < drain 40개` 계산만으로 처리량이 충분하다고 판정하지 않는다. 한 job의 shop 수·페이지 수·API 호출 수·토큰 갱신 시간과 상품/배송 부하까지 측정한다.

CS에서 배송 상태를 보여 줄 때는 기존 주문/배송 조회 모델을 읽는다. 자동 답변 문맥에 주문번호/운송장 정보를 연결하되 다른 주문이나 다른 shop 자료를 가져오지 않는 계약을 검증한다. 이번 CS 계획은 배송 전체 업무의 완성도 판정을 대신하지 않는다.

5. R04: 예정시각을 놓쳐도 이어 가는 복구 스케줄러, 오래된 열린 문의 재검사, 보관기간 부족 경고.

종료 조건: 페이지 2에서 장애→재시작, DB 저장 실패, 다른 shop 실패, 토큰 동시 갱신, 7/35일 중단, 새 고객 메시지와 답변 경합을 통과한다. 저장되지 않은 원문이 완료 범위로 넘어가지 않는다.

### 단계 E — 로컬 검증부터 운영 수용까지

29. V01 전체 실패 분류 및 CS/상품/배송 회귀. 이전 전체 테스트 실패가 기존 문제인지 같은 기준 SHA 실행과 대조한다. `.local` 산출물 lint 범위는 생성 파일만 제외하고 추적 소스의 실패를 숨기지 않는다.
30. V02 승인 관리자 로그인 상태의 실제 로컬 브라우저 검증. 로그인 화면 렌더링만으로 CS 페이지를 검증했다고 보고하지 않는다.
31. V03 복구 가능한 과거 전체 범위에서 원격 ID/페이지/정규화/격리/누락 대조표 작성.
32. V04 로컬 승인 후 운영 적용에 사용할 migration preflight/postflight, 호환 배포/기능 활성화/롤백 문서 준비. 실제 적용은 별도 실행 단계다.
33. V05 채널/유형별 허용된 실제 테스트와 최소 48시간 관측. 미래 영구 무장애를 보증하는 수치로 사용하지 않는다.

**U01/U02 보강 후에도 사용자 지시에 따라 커밋·푸시·배포·운영 SQL 적용은 시작하지 않았다. 로컬 형 검사·변경 린트·DB 동적 검사·빌드는 다시 통과했다. 다음 실행 경계는 migration preflight와 운영 적용, 판매자 계정별 과거 ID 대조이며, 실제 고객 답변은 대상과 문구가 확정된 시험에서만 전송한다.**

## 8. 최종 100% 수용 기준과 증거 형식

각 필수 범위마다 다음을 모두 충족해야 한다.

1. 실제 계정/shop/app과 읽기·답변·Push 권한 및 토큰 갱신이 확인됨.
2. 복구 가능한 전체 과거 범위의 페이지 완료, 원격 대조, 미수집 0. 복구 불가/미제공은 사유와 기간을 공개하고 전체 자동화의 잔여로 관리.
3. 신규 문의와 외부 판매자 답변/재문의/지원 첨부가 지속 수집됨.
4. 웹에서 과거 검색과 전체 대화가 원격 자료와 일치함.
5. 정확한 대상에 답변이 한 번 반영되고 원격 재조회/공식 증거로 확인됨.
6. 중단·토큰 만료·429·중복·역순·응답 유실을 복구함.
7. 실제 적용 코드·DB 함수·worker 경로가 검증 버전과 일치하고 관측 기간을 통과함.

증거 한 행은 `scopeId, channel, account/shop, kind, fixedRange, providerFilter, remoteIdsHash, pageCount, rawRows, normalizedMessages, duplicateRows, quarantineRows, unresolvedRows, job/runId, replyReceipt/readback, codeSha, sqlFunctionHash, observedAt, result`를 갖춘다. 고객 본문과 비밀값은 공유 보고에 쓰지 않는다.

상태는 `코드 있음 / 로컬 검증 / 권한 대기 / 원격 조회 / 과거 대조 / 실제 왕복 / 운영 관측 완료`로 관리한다. **실데이터가 없는 채널은 해당 범위의 0건 대조만 합격하며, 발송/재문의 시험을 통과한 것으로 계산하지 않는다.**

## 9. 소요 산정과 착수 우선순위

지금은 명세·권한 미확정 범위가 있어 전체 완료일을 확정할 수 없다. 개발자를 한 명으로 가정한 계획용 범위는 A 1~2일, B 8~15일, 이미 명세가 있는 C 범위 6~12일, D 4~7일, E 로컬·대조·적용 준비 3~6일이다. 합계 **22~42 개발일**이며 겹치는 공통 구현은 재사용하는 전제다. 이는 실측 일정이나 약속이 아니다. R00/R01/R02 종료 후 작업별로 재산정한다.

Shopee Chat·11번가 상세 계약·Temu Chat/앱 승인, eBay 추가 접근권한, 공급자 보관 범위 밖 export 확보는 위 숫자에 확정 개발량/외부 대기일로 포함하지 않았다. 계약 확보 후 별도 추정치를 붙인다. 실제 왕복/48시간 관측도 수신 가능한 자료와 승인된 시험 일정에 따라 별도로 소요된다. 외부 승인 대기를 일반 코딩 시간으로 환산하지 않는다.

실제 다음 착수 순서는 **R02의 eBay 오류 수정 → R03 진행 위치/부분 저장 계약 → C09 Shopee shop/page 분리 → R04 누락 구간 복구 → R05/C07/C08 Lazada 원문·재개 → 나머지 채널 보완/웹/대조**다. R00/R01의 기준·계정·권한 점검은 각 구현에 필요한 선행 조건으로 함께 진행한다. 로그인/명세 확보만 기다리며 준비된 코드 개선을 멈추지 않는다.
